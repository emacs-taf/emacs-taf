# Workspace development tools

[中文](manual.zh-CN.md)

The workspace owns the shared development commands: `scripts/elisp.py` looks up
and runs Lisp across the checkouts, and `scripts/performance.py` is the one
measurement driver. Packages register their maintained workloads in
`benchmarks/performance-scenarios.el`; they do not implement their own timers,
profiler collectors or baseline comparators. Package runtimes remain ordinary
dependencies of the workloads.

## Look up and run Lisp

`scripts/elisp.py` reads every `.el` file under the workspace checkouts, skipping
hidden directories such as `.jj` and `.worktrees`. A lookup is one command
instead of a search followed by a guessed line range, and a batch run needs no
hand-written `load-path`.

```sh
python3 scripts/elisp.py def ebox-flush etaf-ecosystem-require
python3 scripts/elisp.py refs ebox-flush
python3 scripts/elisp.py run -p etaf-desktop -e '(featurep (quote etaf-desktop))'
python3 scripts/elisp.py run -p ebox -L ebox/tests -l ebox/tests/ebox-active-tests.el -f ert-run-tests-batch-and-exit
python3 scripts/elisp.py check ebox/lisp/ebox-interaction.el
```

- `def SYMBOL...` prints each complete definition form under a
  `;; file:first-last` header, library files before tests, benchmarks and
  examples. Accessors generated by `cl-defstruct` resolve to the struct. A form
  longer than `--max-lines` (250; 0 prints all) ends with its remaining line
  range. When a symbol has no definition the output lists similar defined names
  and the exit status is 1.
- `refs SYMBOL` lists references by file and enclosing top-level form
  (`defun name: lines`), excluding definition sites and comment lines. The first
  line reports the reference count and the definition locations.
- `run` starts `emacs -Q --batch` with `scripts/ecosystem.el` putting the
  checkouts on `load-path`. `-p FEATURE` requires workspace features, `-L DIR`
  adds directories such as a tests directory, and `-l FILE`, `-f FUNCTION` and
  `-e FORM` run in command-line order. Each `-e` value prints without text
  properties. `print-circle`, `print-length` (50) and `print-level` (8) apply to
  the whole run, so cyclic or property-laden structures print finitely.
- `check FILE...` reports delimiters that comments, strings and `?characters`
  hide, printing `FILE: ok`, `FILE: line N: unexpected ')'` or
  `FILE: N unclosed '(' form(s), innermost at line L`. `-` reads standard input,
  so a heredoc probe is checked before Emacs starts. The exit status is 0 when
  every file balances and 1 otherwise.
- `--timeout` (120 s), `--max-rss-mb` (2048) and an output ceiling of 64 times
  `--max-output-kb` stop Emacs. Output beyond `--max-output-kb` (32) prints its
  head and tail and keeps the full log at the reported path. The last line is
  `status=ok|error|timeout|memory|output exit=N seconds=S peak_rss_mb=M` plus
  `log=PATH` when output was cut. The exit status is Emacs's own, 124 when a
  limit stopped it and 2 for a usage error.

## Build a standard package archive

`scripts/package_archive.py` is the shared source-package builder. It produces
ordinary package.el tar files, `archive-contents`, and a checksum `manifest.json`:

```sh
python3 scripts/package_archive.py build --directory /tmp/package-archive \
  --package ecss=/path/to/ecss --package ebox=/path/to/ebox
python3 scripts/package_archive.py verify --directory /tmp/package-archive
```

Each `--package NAME=SOURCE` selects a package entry, its `lisp/` implementation,
and root license/readme files. Add `--resource NAME=DIRECTORY` for runtime data,
including runnable examples exposed by public commands. Missing resources,
symlinks, invalid metadata, checksum changes and an inconsistent index are errors.
Generated bytecode, native binaries, caches and hidden files are not shipped.
Package descriptors are data marked `no-byte-compile`; package.el compiles runtime
Lisp on the installing Emacs. Rebuilding the same inputs produces identical bytes.

The builder needs no network, Git or Emacs. It atomically creates a new output
directory and never replaces an existing one; a failed build leaves no partial
archive. The manifest verifies transport bytes, not publisher identity or runtime
compatibility. Those require release provenance and clean installation checks.
The manifest uses schema 2, with dependency requirements as JSON name/version
pairs. Earlier Ebox-specific schema 1 reports used Lisp strings and are not
accepted as equivalent evidence; rebuild them with this tool. This report-format
change does not change package.el's archive or tar format.

### Build and verify the official selection

Maintainers use Python 3.12+, Git and Emacs for release verification. Users need
only Emacs. Seal the root first, and restore the provider checkouts recorded in
`workspace.json`; building reads those exact Git objects, not their working
copies or current remote heads. `release-dependencies.json` selects packages and
runtime resources, while the root revision supplies the installer.

```sh
make release-build RELEASE_DIR=/tmp/etaf-release-unique
make release-check RELEASE_DIR=/tmp/etaf-release-unique EMACS=/path/to/emacs
make release-tool-tests
```

`release-build` refuses a dirty root, an existing output directory, missing
resources, and an incomplete or too-old dependency closure. The manifest records
the root and provider revisions. Versioned package files must never be replaced
with different bytes; change the package's `Version` header for a new release.

The manifest also records the root revision. Rewriting that sealed commit —
including a message edit — gives it a new identity, so rebuild and rerun
`release-check` before publishing an amended commit.

`etaf-install` packages the root README, LICENSE and CHANGELOG. A release that
changes only one of those root files still changes the
`etaf-install-<version>.tar` bytes; bump `etaf-install`'s `Version` or leave
those files unchanged when publishing another package at the same version. The
publisher refuses a changed versioned tarball.

`release-check` runs each supported target through both the installer and ordinary
`package-install`, in independent `emacs -Q` profiles. It checks dependency origins,
offline reopening, reactive rendering, the actual gallery entry, copying and
running a gallery example, and book data.
Compiler warnings and demoted loader errors fail the check even when Emacs exits
successfully. A new attempt invalidates earlier `installation.json` evidence;
success records the manifest and validator digests plus Emacs, platform and targets.
Keep logs and machine-local evidence private, not in the public package directory.
Repeat with each supported Emacs/platform combination; a run on one platform does
not certify another. GUI rendering and interaction require a separate live check.

For a focused diagnosis, use `scripts/package-release.py verify --directory DIR
--target etaf-ui`; `--direct` runs only ordinary package.el installation. This
narrower evidence does not certify the omitted targets or installation path.

A target that depends on a standard archive can be checked without fetching that
archive for every target. Prefetch one live snapshot, then serve it to the
verification:

```sh
python scripts/package-release.py prefetch --directory /tmp/standard-archives
python scripts/package-release.py verify --directory DIR \
  --target etaf-telega --standard-archives /tmp/standard-archives
```

`prefetch` downloads the GNU, NonGNU and MELPA indexes plus the external
dependency closure declared in `release-dependencies.json`. `verify
--standard-archives` validates the snapshot manifest and serves it on localhost;
`install-smoke.el` reads `ETAF_INSTALL_STANDARD_ARCHIVES` only for this path,
and uses the live archives without it. The snapshot's manifest digest is bound
into `installation.json`.

After the supported environment checks, publish the validated directory with
`make release-publish RELEASE_DIR=/path/to/release`. The command delegates to the
manual site's package-only publisher; it does not rebuild or change site pages.
For the first combined site/package publication, use
`make -C etaf-manual site-publish PUBLISH_ARGS='--packages /path/to/release'`.
See the [site deployment contract](https://github.com/emacs-taf/etaf-manual/blob/main/docs/manual.md#publishing-the-site-and-packages)
for transport, locking, immutable versions, historical downloads and rollback.

`package-release.py stage --directory DIR --output NEW` is the local publication
gate used by that publisher. It requires a sealed workspace manifest matching its
recorded providers, current validator/smoke/manifest digests, and every target through both
installation paths on one recorded Emacs/platform. It refuses
partial evidence and exports only `archive-contents`, a public manifest and its
listed source tarballs. Reports are local evidence, not signatures; this gate
alone does not certify other Emacs versions, platforms or GUI behavior.

The root's `Package installation` GitHub Actions workflow defines batch checks
for Emacs 29.1 and 30.2 on Linux, macOS and Windows. It fetches only the exact
provider commits recorded in the checkpoint, then builds and verifies all targets
through both installation paths without source load paths. It first prefetches
one live standard-archive snapshot for the whole run; each matrix job installs
from that snapshot over localhost, so a throttled archive fails once with its
HTTP status instead of as a missing dependency in every target. The matrix
retry covers only local runner or process failures. No matrix failure is
optional. The prefetch job retains the snapshot and successful installation
jobs retain their machine-readable manifests and reports as CI artifacts; they
do not deploy packages or upload installation logs.
Check every job at the release revision before publication. A workflow definition
is not a passing result, and these batch checks do not certify GUI behavior or a
different development build used locally.

MELPA rate-limits by source IP, and `package.el` reports a rejected request only
as `Failed to download 'melpa' archive`; a 429 is invisible in that message. The
prefetch command prints the HTTP status. Compare a single and a concurrent
request from the affected egress before treating the failure as a dead network.

A POSIX-only pass hides two failure classes: path-flavour comparisons in tools
that walk trees (a `Path` is not a `PurePosixPath` on Windows), and installed
packages whose autoloaded files are resolved through the host's `load-path`
instead of the package's own root. The Windows cell is the platform proof for
both; when a cell fails, read its log rather than guessing from the exit code.

## Publish an install target

`M-x etaf-install` is the single entry users see; `package.el` is the mechanism
underneath it. The bootstrap line `(package-install 'etaf-install)` appears once
because the installer cannot install itself. The accepted contract, including
what is deliberately out of scope, is section 13 of
[the ecosystem contract](architecture.zh-CN.md).

Dependencies split three ways, and each has one owner:

| Kind | Owner | Handling |
| --- | --- | --- |
| Emacs packages, ours or public (`etaf-db`, `telega`) | `Package-Requires` | `etaf-install` registers the archives its targets need (`etaf`, `gnu`, `nongnu`, `melpa`); `package.el` resolves them; signature checks stay enabled |
| Our components (CLI, Node backend, buildable module) | the application repository | shipped in the same tar and checksum; installed into `package-user-dir/etaf/<package>/<version>/`; `npm ci` or `make` runs there with a log; the entry checks the component version at startup |
| System programs and accounts (ffmpeg, mpv, node, TDLib, Godot, login) | the user | detected only; print one platform-specific command; never run `sudo`, `brew` or `apt` |

A target's standard-archive capabilities must cover its whole dependency
closure, not only its direct archive. The installer keeps only the archives
named by the target's capability list when it refreshes for installation;
Telega, for example, names `melpa` for Telega and Transient and `gnu` for
Compat. A missing archive surfaces as `Package 'compat' ... is unavailable`.

A component's source lives in the application repository, never in another
repository or a skill directory, so one version bump publishes the Lisp and the
component together.

Two lanes keep development fast without risking a stale archive:

```sh
# dev: build the working copies, verify installation, never publish
python3 scripts/package_archive.py build --directory /tmp/dev-archive \
  --package etaf-md-preview=etaf-md-preview
ETAF_INSTALL_ARCHIVE=/tmp/dev-archive ETAF_INSTALL_PROFILE=/tmp/profile \
  ETAF_INSTALL_TARGET=etaf-md-preview emacs -Q --batch -l scripts/install-smoke.el

# release: sealed commits only, version bumped, full gate, explicit publish
make release-build RELEASE_DIR=/tmp/release-next
make release-check RELEASE_DIR=/tmp/release-next
make release-publish RELEASE_DIR=/tmp/release-next
```

Adding a package to the archive is a fixed sequence; do not invent another route:

1. Keep the package in a recorded repository: framework providers go in the
   `repositories` section of `workspace.json`, applications in its
   `applications` section, both pinned to a published commit.
2. Declare `Version` and every Emacs dependency in `Package-Requires`; put
   components and runtime resources inside the repository and list resource
   directories in `release-dependencies.json`. The entry must also resolve its
   own `lisp/` while the byte compiler runs: prefer
   `byte-compile-current-file`, then `load-file-name`, then
   `buffer-file-name`. An archive install otherwise reports
   `Cannot open load file` for the modules.
3. Implement `<package>-doctor` returning `(LABEL AVAILABLE REMEDY)` facts, and
   mark blocking versus degraded capabilities; the installer aggregates them.
4. Add the target to `etaf-install--targets` with its group and open command so
   the menu shows its status before installation. Add the same package to the
   application or game list in `scripts/install-smoke.el`, which reopens and
   diagnoses it as an installed package during the release gate.
5. Run the package's `make check`, then the dev-lane install on Emacs 29.1, 30.2
   and 31.1 (29.1 lives on `lightos`, see the host notes).
6. Commit and publish the provider, record it in `workspace.json`, build the
   sealed archive and run `make release-check`; commit and publish the root.
7. Publish with `make release-publish`, then read back `archive-contents` and the
   package page over HTTPS.
8. Republish the site when pages or the book changed, and let every cell of the
   six-cell installation workflow pass on the published commit.

Future installer commands use the `etaf-install-` package prefix; `etaf-` is
reserved for the framework. A manage interface must be a native
`tabulated-list` buffer because it has to work before ETAF is installed; it
must not depend on `etaf-ui`. Package lifecycle remains owned by `package.el`.

Installed targets are managed with `M-x etaf-install-manage`. It shows installed
and available versions, runtime readiness and dependencies, and offers
package.el-backed install, update, remove, open and doctor actions.
`etaf-install-update`, `etaf-install-remove` and `etaf-install-status` expose the
same lifecycle to callers; removal keeps application data and logins.

A missing runtime tool is part of the installation report, not a silent
success: the install message names the first remedy and the doctor lists every
required and optional fact, while the manage echo repeats the selected target's
remedy. `etaf-telega` installs the Emacs `telega` package, but its native
`telega-server` is a TDLib build supplied by the user; that remedy names
`M-x telega-server-build` and the Telega installation guide.

Never edit files under `/srv/etaf.top` by hand: the deployer owns locking,
immutable versions, checksum verification and rollback.

## Run a measured change

```sh
make perf-list
python3 scripts/performance.py run --mode batch --scenario 'ebox.focus.*' --diagnose
python3 scripts/performance.py run --mode gui --scenario gallery.selection.mouse --diagnose
```

Use `--scenario` repeatedly to select a related group. `--scenario-file FILE`
loads an additional explicit workload entry; `--load-path DIR` adds a public
package root. GUI runs use the existing `emacsclient` server and normal Emacs
configuration. `--server NAME` selects an existing named server. GUI measurement
allows background operation by default and records focus before and after every
sample. Keep the rendered window available and avoid editing its test buffer.
Background timing does not certify foreground input latency. `--foreground`
activates the current frame once and requires focus during latency samples;
`--focus-policy foreground` requires focus without activating it. Diagnostic
passes always allow background execution and retain their actual focus state.
Window-scoped screenshots and recordings do not require foreground activation.
On macOS, App Nap can throttle a background Emacs, so background samples then
measure the throttle instead of the code. Confirm a dedicated measurement Emacs
is not throttled by running a pure Lisp loop there and in batch Emacs. If it is,
disable App Nap for the app while measuring (`defaults write org.gnu.Emacs
NSAppSleepDisabled -bool YES` before starting it, `defaults delete org.gnu.Emacs
NSAppSleepDisabled` afterwards); `-NSAppSleepDisabled` cannot be passed as a
command-line argument because Emacs rejects unknown options before its GUI layer
sees them.

Finish compilation before GUI acceptance. Preflight records the process, package
origins and loaded files. It rejects another checkout, an active profiler, and
loaded packages edited or rebuilt after Emacs started. Restart the same native
Emacs and run `M-x server-start` to establish a fresh code generation. This is a
conservative freshness check; the tool does not hot-reload package implementations.

Every sample records the actual loaded files for selected package entries,
`lisp/` implementations and `examples/` application code before and after timing.
Explicit benchmark adapters are excluded. `runtime_code` summarizes these as
`compiled`, `interpreted`, `mixed`, or `not-applicable` when no selected runtime
library was loaded. `.elc` records mean compiled loading and may also represent
native code in Emacs's load history; they do not prove bytecode-only execution.
Detailed file paths and formats remain available for diagnosis.
Native artifacts use Emacs's known source-origin mapping when available.
External `.eln` files without a known origin are retained separately as
`unmapped_native_libraries`; their ownership cannot be established, so they
are outside the classified package scope. This is library-loading evidence,
not a claim about every dynamically redefined function in the process.

Mixed formats, missing evidence or a format change during a scenario leave the
run unverified. Comparisons require the same execution strategy, while allowing
different checkout paths or additional compiled modules. Two entirely interpreted
runs remain comparable. Existing `.elc` files and `native_jit` alone do not prove
compiled execution: a newer source can win under `load-prefer-newer`. Recompile
the intended checkout for a compiled comparison; the tool never alters file
timestamps or rebuilds code to make the evidence appear fresh.

Defaults are three sets with five recorded warmups followed by ten formal latency
samples per scenario and set. `--warmups N` changes the warmup count; zero is useful
for a cold screen. Warmups use the same preparation, timing, settlement, foreground
policy and correctness checks as formal samples. Their timings, results and failures
remain in the evidence, but do not enter formal latency percentiles or budget checks.
The separate 500 ms hard limit applies to both warmups and formal interactions.
No warmups are inserted into the separate diagnostic passes. Batch sets use
fresh Emacs processes per scenario and set, isolating unrelated workloads' caches
and retained state; GUI sets use fresh fixtures in the same native process.
Scenarios marked `series` retain their fixture within one set and declare that
steady-state condition in the catalog; their warmups and formal samples share that
fixture. The driver leaves an already displayed fixture in its window rather than
reinstalling the buffer between samples, preserving its window presentation and
continuous rendering. It still switches buffers when the target changes and
redisplays before timing and at settlement. Fresh-isolation scenarios keep
recreating their fixture for every operation.
Setup is outside the timed operation.
For a quick screen, use `--sets 1 --samples 3`; it cannot certify repeatability.
The sample-coverage gate requires at least three sets, thirty formal samples per
set and five warmups per set (`--sets 3 --samples 30 --warmups 5`). A smaller run
remains a screen even when all its measured operations meet the latency budget.

Record a baseline by keeping the resulting `result.json`. Compare a change with:

```sh
python3 scripts/performance.py run --mode gui --scenario gallery.selection.mouse --foreground --baseline /path/to/baseline/result.json
python3 scripts/performance.py compare /path/to/before/result.json /path/to/after/result.json
python3 scripts/performance.py summarize /path/to/result.json --scenario gallery.selection.mouse --details
```

Every sample must pass the scenario's visible/semantic verification and context
checks. All slow samples, including GC, remain in the report. Each scenario has
its own formal maximum-latency budget and there is a separate 500 ms hard limit
covering warmups too. A
baseline comparison checks p95 and maximum independently, with a 2 ms regression
allowance. Different workloads, drivers, warmup protocols, sample coverage, focus/display conditions or machines
are incomparable. Changed source revisions are expected and recorded.

Gallery fixtures synchronize Ebox's layout viewport after the buffer is displayed,
before timing any interaction. Batch Gallery fixtures use 160 character widths and
50 lines. The versioned workloads distinguish this setup from earlier samples
whose hidden initial mount had no resolved layout viewport. Existing-page scenarios
borrow the caller's current viewport without resetting it.

`passed` means the selected latency gate passed; `failed` means measured latency
or a baseline gate failed; `screened` means a smaller valid run completed;
`unverified` means evidence is missing, invalid or incomplete. Exit codes are
0 for a completed passing/screening run, 1 for a latency regression or budget
failure, and 2 for invalid evidence. A completed operation is not automatically
a performance pass. `acceptance_eligible` separately records sufficient sample
coverage. `make verify` compiles the workspace, runs the registered Playground
batch scenarios through this driver, then runs the complete correctness gate
even if performance failed. Its `performance/result.json` is an ordinary driver
report. A one-set run is `screened`; use `scripts/verify.py --record-baseline
--repeatability` for a three-set baseline. Comparison adopts the baseline's
sample grouping and uses this driver's validity, workload and regression checks.

## Gate a change in the GUI

`gate` is the quick per-change check. It runs every selected scenario that
declares `:gate` back to back inside an existing GUI server, typically a full
matrix in a minute or two, and judges fixed budgets. Use `run` for diagnosis,
baselines and the final three-set acceptance.

```sh
python3 scripts/performance.py gate --server fg --scenario-file ebox/benchmarks/performance-scenarios.el --scenario '^ebox\.'
python3 scripts/performance.py gate --report ~/.cache/emacs-taf/gate/<run>.json
```

Each sample times `:invoke` (the operation) and the following forced redisplay
(end to end), after five untimed warmups, and records the conses the operation
allocates, excluding the measurement's own. Timed samples run unobserved; a
twin uses a second, untimed pass from a snapshot of the buffer. The
scenario files load from their byte-compiled copies when those are current,
because applications run compiled code. The
scenario's `:gate` plist selects a class; a trailing numeric id component is the
size, which `rows` uses as the row count unless `:rows` is given:

| Class | Operation budget (p50 unless noted) |
| --- | --- |
| `local` | 50 µs, p95 200 µs, conses 200 |
| `propagate` | 200 µs |
| `structure` | 300 µs at every size |
| `counter` | 30 µs, conses 200 |
| `snapshot` | 2 ms at every size |
| `resize` | 16 ms |
| `rows` | 40 µs per row |
| `info` | reported only |

For `local` and `propagate`, the largest size of a family may not exceed
1.5 × the smallest size's operation p50 plus 20 µs. A `structure` or `snapshot`
update compares or copies the new list, so its operation may grow with the list
within the budget. `:twin diff`
requires `:observe` reports with `:ranges`, a list of `(START OLD NEW)` line
replacements in application order. The runner converts each sample's ranges
into the smallest plain-buffer edit producing the same text and properties,
replays it on the snapshot without moving point (Emacs redraws
an edit on the line at point through a faster path) and requires the end-to-end p50 to
stay within 200 µs of that floor; `rows`, `structure` and `snapshot` compare the
redisplay time after the operation instead, because their budgets already bound
the operation. Ranges
that do not reproduce the live buffer fail the scenario. `:twin replay` times the second pass's `:invoke` on the snapshot shown in
the selected window, so its operation must act on the current buffer. Exit
status is 0 for a pass, 1 for a failed budget, verification or twin, and 2 for
an incomplete report.

## Capture a terminal session

`scripts/tui-capture.py` runs a command in a real pseudo-terminal and saves the
final screen, so terminal (TUI) layout is judged from what the terminal shows
instead of from a GUI frame. It needs `pyte` and `Pillow`
(`pip install pyte pillow`).

```sh
python3 scripts/tui-capture.py --cols 80 --rows 24 --out /tmp/app.png -- \
  /opt/homebrew/bin/emacs -nw -Q -l /tmp/probe.el
python3 scripts/tui-capture.py --cols 120 --rows 40 --out /tmp/app-wide.png -- \
  /opt/homebrew/bin/emacs -nw -Q -l /tmp/probe.el
```

The command after `--` runs with `TERM=xterm-256color` and truecolor support in
a pty of `--cols` x `--rows` cells. `--out` receives a PNG and `<out>.txt` the
same screen as text: one line per row, without trailing blanks, a wide
character kept as the single character the screen holds. The image is drawn
with Sarasa Mono SC when present, then Menlo, then DejaVu Sans Mono, and
`--font PATH[:INDEX]` selects another face (INDEX picks a face from a font
collection).

The text file is what assertions read; the image is what alignment, borders,
icons and overlays are checked in. Capture 80x24 for a narrow window and 120x40
for an ordinary one, one image per size rather than a scaled copy. The tool
ends with an `exit=` line carrying the command's own status, and `--timeout`
(90 s) still writes the screen captured so far and exits 124. Both files are
written after a failed or timed-out run; a missing module, an unreadable font or
an absent command is reported in one line instead of a traceback.

## Validate an isolated checkout in a real GUI

A `jj workspace add` checkout must be exercised in the full user configuration
without ever loading the main checkout's code generation. The user init reads
`emacs-taf-dir` for package roots, but `init-etaf.el` and eager `use-package`
forms also add `~/emacs-taf` paths, and an added path wins the resolution.

1. Put a private `site-start.el` first on the load path with
   `EMACSLOADPATH=<private directory>:`. It runs before the init file, so it can
   `setq` (never `defvar`) `emacs-taf-dir` to the isolated root, set a private
   `server-name`, `load-prefer-newer` and a bounded `kill-emacs` watchdog, and
   advise `require` and `load` to redirect `~/emacs-taf` libraries and relative
   names to the isolated root. Advising `load` alone is not enough: Emacs 31's
   `require` does not call the advised subr.
2. Start a background instance with
   `open -g -n -a Emacs --env 'EMACSLOADPATH=<private directory>:' --args -l
   <start file>`. The start file runs after the init file: it puts the isolated
   roots first, removes the `~/emacs-taf` entries, starts the named server and
   records its PID. Background measurement must not be App-Nap throttled; check
   it as described in [Run a measured change](#run-a-measured-change) instead of
   passing `-NSAppSleepDisabled`, which Emacs rejects as an unknown option.
3. Prove one code generation before measuring: `locate-library` for every
   provider and the `(provide . feature)` entries in `load-history` must all
   resolve under the isolated root. The performance driver repeats this in its
   preflight and rejects a library loaded from another checkout. Confirm each
   checkout follows its published main first: a jj workspace keeps its own
   working-copy commit, and `workspace.py status` reads the primary checkout's
   bookmarks, so an isolated checkout can sit behind main and invalidate both
   the measurement and the recorded revision.
4. Run `scripts/performance.py run --mode gui --server <name> --root <isolated
   root> --load-path <app root>` and close the instance by its recorded PID,
   never by process name.

When writers change the primary checkout, snapshot the measured source generation to avoid
`UNVERIFIED: Workspace sources changed during measurement`:
copy `workspace.json` and each loaded repository (ecss, ekp, ebox, etaf,
etaf-ui, and etaf-gamekit/etaf-games or the app) with `rsync -a --exclude .jj
--exclude .git ~/emacs-taf/<repo> /tmp/<snapshot>/`, substituting a `jj workspace
add` checkout where a repository change is not in the primary tree. Apply the same
site-start redirection and start file with `--root /private/tmp/<snapshot>` and
matching `--load-path`;
macOS needs the `/private/tmp` truename because preflight compares truenames.
Report contained commits and uncommitted provider work, delete the snapshot after the run,
and still finish with quiet-tree `make verify` on the integrated checkout.

The two helper files belong to one measurement session, not to the checkout;
keep them under the system temporary directory.

### Verify installed packages in the full user init

Install the release into a disposable `package-user-dir` with the maintained
installation smoke probe, then use the two private startup files described above.
Load the tested providers from that ELPA directory in `site-start.el`, before the
user init can require source checkouts. After init, remove checkout load paths and
check both `locate-library` and each provider's `load-history` entries. The gallery
command and implementation must also resolve inside the installed package.
The server can accept connections before the command-line startup file finishes:
wait for the post-init profile and provenance checks to complete before driving
commands, not merely for a responsive server socket.

Do not unload a running full-init dependency graph to switch generations: unrelated
applications and global hooks may still reference its functions and variables.
Keep unrelated init code intact, stop its public idle modes if they would interfere,
and verify only the installed providers and target application. If descriptors
need rescanning after the early loads, use `(package-initialize t)`; reactivating
facade autoloads over already loaded command autoloads can create a second load
chain. Use normal activation in a fresh user profile.

Exercise the installer's standard completion with the user's completion frontend,
then native activation, Theme switching and help in the installed gallery. Capture
the owned window without changing application focus, inspect the images, and close
the verification instance on success or failure. Keep helper files and captures
outside Git. A full-init pass does not replace the separate clean `-Q` install gate.

## Read the diagnosis

`--diagnose` runs three additional passes after latency sampling:

| Pass | Evidence | Interpretation |
| --- | --- | --- |
| Trace | Public provider reports: Runtime operations and the Ebox flushes inside them | Locate the expensive part of the data flow. |
| CPU | Sampled self/inclusive weights, call stacks, function names and source locations | Find candidate functions to investigate; weights are estimates, not exact per-call times. |
| Memory | Allocation weights and call stacks | Explain allocation pressure and GC; allocation is not proof of a leak. |

These diagnostic samples never enter latency statistics. CPU and allocation
profilers run separately, without the provider recorder. Low CPU sample counts
are explicitly identified; increase `--diagnostic-samples` for a targeted case.
No GC threshold is changed by the driver. Before/after GC settings are recorded
as dynamic state because the framework can temporarily change them during its
documented render burst. Font, geometry, target, backend capability and source
generation remain validation conditions.

Ebox's public observer reports each flush with its `strategy` (`lines` or
`full`), the number of node `edits`, the buffer `lines` written and its
duration. ETAF forwards those reports only inside a Runtime operation (Event,
Action, mount, refit, or an `etaf-performance-call-operation` body), so a
workload that writes and flushes outside one yields no flush evidence. The
summary prints the medians of Ebox flush time, time outside Ebox and lines
written, plus the count of each flush strategy. Time outside Ebox includes
application code, reactive propagation, input dispatch, asynchronous waiting
and driver overhead. Medians of separate quantities need not add up to the
median of whole operations.

Investigation hints identify a full repaint during a local update, GC inside an
interaction, too few CPU samples and missing flush reports. They point to
evidence and do not assert a root cause. Inspect the flush costs and stacks
before changing architecture.

An adapter's optional `:outcome` callback reads a bounded, JSON-safe result through
public APIs after timing and profiling stop. It must not change application state.
The result is saved with that exact latency sample; detailed summaries show the
slowest sample's outcome. This does not capture earlier flushes within the same
input; use the separate trace pass for the full sequence.

## Measure the incremental commit

A state write marks only the retained nodes its bindings reach. Ebox relayouts
the smallest boundary whose outer size is unchanged and rewrites the affected
buffer lines; a structural change or a size change that escapes every boundary
widens the region. Mount, a viewport change and an explicit refit repaint the
whole buffer, and so do overlapping line replacements. Read the actual path
from the flush reports.

Use the registered workloads to separate a local row update, structural append and
an ordinary catalog control. Run the initial diagnosis with a small sample count:

```sh
python3 scripts/performance.py run --mode batch \
  --scenario row-update.30 --scenario row-update.400 \
  --scenario list-append.30 --scenario list-append.120 \
  --scenario gallery.selection.steady.callback \
  --sets 1 --samples 5 --warmups 2 --diagnose --diagnostic-samples 4
```

For repeatability, keep profiling separate and initialize three independent sets:

```sh
python3 scripts/performance.py run --mode batch \
  --scenario row-update.30 --scenario row-update.400 \
  --scenario list-append.30 --scenario list-append.120 \
  --scenario gallery.selection.steady.callback \
  --sets 3 --samples 30 --warmups 5
```

Keep the printed evidence directory. Add `--baseline /path/to/result.json` to the
same repeatability command after a change, with the same workload and environment.
Inspect a particular result with:

```sh
python3 scripts/performance.py summarize /path/to/result.json \
  --scenario gallery.selection.steady.callback --details
```

The row workloads retain a fixed number of rows and change the first row's paint
and weight. Append workloads start with the named size and keep growing within
each set, including warmups. They are not fixed-size single-insertion experiments.
The Gallery callback workload measures the complete local callback, settlement
and flush boundary; it does not certify keyboard or mouse input. Batch results
do not certify graphical redisplay or foreground input latency. Use the
corresponding registered GUI workloads for those boundaries.

Interpret the flush reports together:

| Evidence | Interpretation |
| --- | --- |
| `strategy` | `lines` rewrote only affected lines; `full` repainted the buffer: expected for mount, viewport change or refit; on a local update it means the damage overlapped. |
| `edits` | Node changes the flush consumed; compare with the size of the state change. |
| `lines` | Buffer lines rewritten; a local update should stay proportional to the changed rows, not the document. |
| Ebox `ms` and time outside Ebox | Whether cost sits in layout and buffer writes or in application and reactive work. |
| GC and allocation stacks | Included pauses and allocation candidates; separate runtime work from driver serialization and other measurement overhead. |

Correctness, flush strategy and latency need separate conclusions. Background
GUI timing also needs the App Nap and focus checks described above; it must not
be presented as foreground input certification.

The cross-package cost model and required acceptance matrix are maintained in
the [ecosystem architecture](architecture.zh-CN.md). This workflow explains how
to obtain evidence; it does not make pending architecture targets implemented
behavior.

## Judge Ebox interaction ownership

A press or `ebox-activate` resolves the node that owns a buffer position.
Judge that ownership with the framework's own spatial facts, never by reading
the rendered line text: one buffer line interleaves cells from different
columns, and a multi-row cell's lower rows are blanks that still belong to its
hit area.

```elisp
;; In a probe, with the view mounted and EXPECTED the node that should own it:
(let* ((node (ebox-node-at position buffer))
       (bounds (ebox-node-bounds expected t)))
  (list :owned (and node (or (eq node expected)
                             (ebox-node-ancestor-p expected node)))
        :inside (and bounds (<= (car bounds) position (cdr bounds)))))
```

`ebox-node-at` returns the innermost node painted at a position and
`ebox-node-bounds` with ALL-LINES returns `(START . END)` from the node's first
visible cell to the end of its last painted row. A resolution is correct only
when the painted node lies inside the expected owner and the position lies
inside its bounds. From ETAF, use `etaf-host-ref-bounds` with a Host reference
instead. Blank cells such as a flex gap, a box's padding or a multi-row cell's
lower rows still carry their owner's keymap, so the bounds check stays the
acceptance test.

## Evidence and failure handling

Evidence defaults to `~/.cache/emacs-taf/performance/` (or `$XDG_CACHE_HOME`).
`--output-dir DIR` selects an empty directory. Existing evidence is never
overwritten. `result.json` is the compact comparison/report entry; per-set JSON,
configuration files, profiler summaries and logs preserve the complete run.
During a pass, the per-set JSON is a bounded progress snapshot: `samples` is
empty, `sample_count` counts committed rows, and `sample_journal` names its
adjacent append-only JSONL file. Each completed sample is written once. The
runner polls progress without rereading the journal; after completion it writes
the usual complete JSON report. This avoids repeatedly serializing all earlier
samples on Emacs's interaction thread. If Emacs exits or cannot answer, the
runner recovers complete journal rows; a torn final line or missing committed
row keeps the run unverified rather than losing earlier evidence.
Every raw row records `phase` (`warmup`, `latency` or `diagnostic`), its per-phase
sample number and continuous operation `iteration`. The summary's `warmups` keeps
counts, maximum, all timings and failures; `all_latency` reports the combined
warmup/formal count, maximum and failures, including first use. `attempted_count`
also includes an interrupted operation without a completed timing. An unavailable
maximum stays null; the failure and active stage remain visible. Slow warmups never
disappear behind a passing formal distribution, and a failed warmup invalidates the
run. Progress records the scenario, set, phase, sample and stage before setup or
invocation.

`--timeout` bounds a setup/action/settlement step; `--run-timeout` bounds each
set. A timed-out batch process owned by the tool is terminated. A GUI timeout
requests cancellation through the same server and leaves Emacs running. If
Emacs itself cannot answer, the report retains the active stage; interrupt the
stuck operation with `C-g`. `python3 scripts/performance.py cancel` cancels the
current tool job. A failure preserves its partial evidence.

GUI timing ends when the explicit settlement predicate succeeds and forced
redisplay returns. It does not measure physical hardware input or OS compositor
presentation. Batch results do not certify GUI latency. Visual appearance still
requires the maintained GUI workflow and inspection of a current window capture.

The final GUI fixture normally remains owned by the runner until the next run;
when the job stops, the benchmark window shows the buffer it displayed before
the run and the fixture buffer stays alive for inspection.
To keep that page for manual interaction or an existing-page scenario, call
`(taf-benchmark-detach-fixture)` through the same emacsclient after the job stops.
It returns the live buffer, transfers cleanup ownership to the caller and leaves
the application mounted. A call during an active job signals an error.
Existing-page adapters must leave that borrowed buffer mounted in their cleanup.

## Register a scenario once

The supported registration and fixture API is documented in
[`performance-driver.el`](../benchmarks/performance-driver.el). A scenario owns
its application setup, action and verification; the shared driver owns execution.
Use only provider interfaces declared by their public entries.

```elisp
;;; -*- lexical-binding: t; -*-
(taf-benchmark-register
 "example.counter" :version 1 :modes '(batch gui) :budget-ms 10
 :impact 'local :isolation 'series :description "One visible counter update"
 :setup
 (lambda (_mode)
   (let ((buffer (generate-new-buffer " *Counter benchmark*")) (count 0))
     (list :buffer buffer
           :invoke (lambda (_sample)
                     (with-current-buffer buffer
                       (erase-buffer) (insert (number-to-string (cl-incf count)))))
           :verify (lambda ()
                     (with-current-buffer buffer
                       (equal (buffer-string) (number-to-string count))))
           :cleanup (lambda () (when (buffer-live-p buffer) (kill-buffer buffer)))))))
```

`:prepare` resolves input targets after the GUI buffer is displayed, before the
timer starts. `:ready` waits for initial loading, and `:settled` defines the
completion of asynchronous actions (5 ms polling resolution is recorded).
`:observe` accepts a report sink and returns a cleanup/collection function,
called after timing and profiling stop. `:required-providers` detects missing
expected observations. `:environment` returns JSON-safe capability facts.
A fixture may declare `:disposes-buffer t` for a close/unmount operation. Its
target must be live on entry and dead on exit; frame, window, font and other
context checks still apply. Missing disposal, undeclared target loss or a
simultaneous context change fails the gate. Records retain the target-death
fact and both contexts; the flag alone never exempts validation.
Verification returns exactly `t` or a short failure string. Cleanup releases only
the fixture's resources. The final GUI fixture stays available for inspection.
The `:invoke` index starts at zero for each scenario/set and advances continuously
through warmups and formal samples; diagnostic passes have their own index sequence.

Keep scenario inputs, versions and verification stable across an A/B comparison.
Register new application scenarios with their owning package and validate the
adapter; subsequent runs require only the shared command. The tool's command,
timeout, asynchronous, failure and comparison regressions run in workspace
`make check` through `tests/tools/test_performance.py`.
