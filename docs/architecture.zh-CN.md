# Emacs TAF 生态架构与开发规范

本文是后续跨仓库开发的输入契约，汇总已确定的生态定位、样式表达、渲染与交互数据流、ETAF 组件与 API 易用性，以及能力扩展边界。这里的“必须”表示开发约束；“目标”表示已确定但尚未全部实现的行为，不代表当前版本已经支持。

集成版本见 [workspace.json](../workspace.json)。各包的入口 Commentary、手册和架构文档描述已实现的公共契约；完成能力变更时同步更新这些契约和本文的剩余要求。

## 1. 目标与范围

目标是构建可持续发展的 Emacs 文本应用生态。底层包必须可以独立使用，上层通过公共契约组合它们，应用获得统一的样式、布局、交互和增量更新行为。

- 保持各仓库独立的 Git 历史、发布和公共接口；工作区负责编排与集成检查点，不改成 monorepo。
- 每项能力有明确的权威所有者；消费者可以提供上下文或策略，不能维护另一份具有相同职责的权威状态或算法。
- 保留不同层次的必要抽象，例如组件失效计算与渲染影响计算；不能仅因都叫“响应式”或“增量”而强行合并。
- 先满足已有应用场景，再提炼重复能力。暂不新增通用响应式包、事件包或浏览器式运行时。
- 从应用作者的角度降低理解成本和重复代码：普通应用不应要求了解保留节点、内部身份、调度器或回调缓存，才能正确组合组件、状态和事件。
- 本文指定行为与边界，不预先虚构尚未实现的公共函数名，也不承诺任意 GUI 能力或零运行时开销。

## 2. 包定位与依赖方向

| 包或仓库 | 权威职责 | 边界与依赖 |
| --- | --- | --- |
| ECSS / `ecss` | 通用选择器、优先级、层叠、继承、变量与计算样式 | 不依赖 Ebox 或 ETAF；计算结果是数据，不负责 buffer、布局或应用响应式状态 |
| EKP / `ekp` | 独立的 Knuth–Plass 段落排版能力 | Ebox 特定换行模式的可选依赖，不成为普通布局的强制安装成本 |
| Ebox / `ebox` | 保留节点树、文本测量、Box/Flex/Grid、样式投影、滚动、重新布局边界、行合成、直接改写 buffer 区段、几何增量更新及通用宿主输入原语 | 必需依赖 ECSS；按需使用 EKP；不依赖 ETAF。就窗口相关能力而言，它只发布几何和图层事实以及手势阶段，不实现窗口或桌面语义 |
| ETAF / `etaf` | View、Component、应用状态、Context、Effect、Action、Data、生命周期及可复用的交互行为（例如把手势位移应用到受控几何状态） | 通过 Ebox 公共节点操作创建和修改界面；显示变化只经 Ebox flush 写入 buffer，不绕过 Ebox 修改显示；不维护第二套布局、命中或焦点权威 |
| ETAF UI / `etaf-ui` | 可复用控件及控件语义，例如 Button、Checkbox、表单组合、可移动/可调整大小的面板外壳 | 依赖 ETAF；消费 Ebox 的布局和输入原语以及 ETAF 的交互行为，不实现另一套命中、焦点或布局系统；不拥有应用级窗口工作区策略 |
| `etaf-db` | ETAF 数据库后端接入，目前实现 SQLite | 唯一包入口为 `etaf-db`；SQLite 专用 API 保留 `etaf-sqlite-*`，复用核心 Data Source 契约 |
| `etaf-gamekit` | 游戏定义、独立运行实例、异步动作与观察结果、生命周期和后端适配 | 核心只依赖 ETAF 公共 API，不含游戏应用或启动菜单；规则、搜索、世界状态和原生存档归后端，应用拥有呈现并按需使用 ETAF UI；交互格子和被动字符行归 UI 目录组件 |
| `etaf-desktop` | 基于 ETAF 和 ETAF UI 的 Emacs 桌面管理应用：应用注册与实例生命周期、窗口模型、工作区、z-order、焦点、浮动/平铺布局树、移动/调整大小、最小化/最大化/还原、会话和应用级命令 | 依赖 ETAF 与 ETAF UI；通过其公共 API 使用 Ebox 几何和手势能力，并组合 UI 的窗口、任务栏、启动器、切换器和分割器；窗口策略和业务状态只在此应用层拥有，不下沉到 Ebox、ETAF 或 UI |
| `ebox-playground` | Ebox 独立使用示例与预览工具 | 使用 Ebox 公共接口；示例专用依赖与预览工具的运行时依赖分开 |
| `etaf-playground` | ETAF/ETAF UI 及生态集成示例和验收入口 | 按示例需要使用 ETAF、UI 和数据适配器；只消费已发布的公共行为，不承载可复用窗口管理或桌面策略，不能反向成为核心依赖 |
| `etaf-manual` | 核心包（ecss、ekp、ebox、etaf、etaf-ui、etaf-db）的参考手册：为全部公共接口各写一个定义条目，用概念和公共接口讲清各子系统的机制，中英双语；`etaf-manual` 包把全书作为数据供 Emacs 工具和网站构建读取 | 运行时依赖 ETAF 与 ETAF UI（挂载可运行示例）；门禁读取各核心包入口的 Commentary 记录与版本，签名、公共名字、版本或译本结构不符即失败；只记录公共接口，各包维护者的 `docs/architecture.md` 仍归各包 |

Ebox 独立使用意味着调用者无需 ETAF，且普通用户无需亲自调用 ECSS 的计算接口。它不意味着 Ebox 没有底层依赖。样式表可以不用，ECSS 作为统一样式引擎仍是必需依赖。

原生加速器只加速所属层的计算，不取得另一套语义或显示写入权威。启用、禁用和不可用时的行为必须遵循提供方公开契约；可选依赖缺失不能静默改变用户明确选择的排版语义。

GameKit 的应用入口是游戏定义与独立实例，统一边界是动作、观察结果和生命周期。
游戏项目拥有自己的规则、资源、视图和启动命令，后端选择属于游戏配置。
框架不要求所有游戏使用同一运行时，也不把世界强制投影成棋盘、故事或字符网格。
每个游戏定义自己的版本化观察数据，ETAF 应用通过公共组件组合地图、面板、
表格、图片或视频等呈现。资源 ID 由应用内容清单解析，二进制素材与视频帧不混入
状态消息。独立游戏仓库与框架 examples 中的应用使用同一组公共接口。

当前包含 Godot、boardgame.io 和 OpenSpiel 适配器：分别用于无窗口实时模拟、
应用自定义回合与阶段规则、已有的顺序或同时行动规则内核。运行游戏只需安装
所选后端；统一接入契约不表示原生规则可以互换，也不表示原生游戏目录中的每个
游戏都已通过前端验收。

实时样例 Salvage Station 位于 `etaf-salvage/`，使用 Godot 的物理碰撞、
固定步长模拟和寻路；Godot 不承担此样例的画面和输入。ETAF 前端提供地图、目标
检查、货舱、技能、日志和存档交互。棋类、麻将等专用规则或 AI 内核按具体游戏
选择，尚未接入的候选不作为默认依赖。轻量经营游戏可以保留独立的进程内状态
内核，不必为了统一而增加外部进程。

GameKit 不提供统一世界模型、联网同步、素材下载或音频混合服务。详细选型依据
与已实现边界维护在包内架构文档；协议和恢复约束维护在包内手册，公共接口以
`etaf-gamekit.el` 为准。没有远程的本地检出尚未纳入工作区已发布版本清单；
包级检查和独立 GUI/性能验收仍须完整执行。

## 3. 样式只有一套语义

### 3.1 表达形式

样式输入使用有序规则列表；每条基础规则采用 `("SELECTOR" :PROPERTY VALUE...)`。不要求额外的 `styles` 头部。

静态 `.ecss` 文件直接保存一个数据表达式：

```elisp
((".title" :color "#334155")
 (".title.active" :font-weight bold))
```

在普通 Elisp 求值位置，遵循正常的引用规则：

```elisp
(setq application-styles
      '((".title" :color "#334155")
        (".title.active" :font-weight bold)))
```

ETAF Component 的静态声明片段是：

```elisp
:styles
((".title" :color "#334155")
 (".title.active" :font-weight bold))
```

这里保留 `:styles`，因为它标明组件定义中的样式字段；规则列表内部不再重复 `(styles ...)`。该规则列表输入由 ECSS 共享读取器和 Ebox schema 校验；ETAF 的组件规则与主题默认值通过共享作用域交由 ECSS 匹配和层叠。静态宏字段按数据读取，普通变量、属性表达式等仍按其公开的 Elisp 求值契约执行；两者不能混用。

静态 `.ecss` 加载只读取并验证一份规则列表，不执行 `eval`，不在样式数据中隐式调用函数。多余顶层表达式和不合法结构必须报错。动态计算通过 Elisp 和明确的公共接口提供，不能让各 Playground 自己发明执行约定。

规则顺序、选择器解释和声明校验必须收敛到共享的 ECSS 语义及 Ebox schema。文件读取、组件字段与程序构造可以有不同入口，但不能形成不同的规则语言。高级层叠能力继续通过 ECSS 契约表达，不因这个基础列表示例而丢失。

### 3.2 所有权与计算

- ECSS 负责选择器匹配、specificity、层叠顺序、继承和计算样式；ETAF 不再保留简化匹配器或“第一条匹配填空”的算法。
- Ebox 定义布局与绘制属性、校验、简写展开和计算结果的显示投影；节点上的行内声明也进入统一样式语义。
- ETAF 提供组件样式所有权、主题上下文和作用域事实，通过公共适配接口交给 Ebox/ECSS；不得先算出另一套获胜属性再覆盖结果。
- 行内属性、主题默认值和组件规则映射到明确的 ECSS 来源与作用域。不能用“行内永远赢”等简化口诀覆盖 `important`、层和继承的完整规则。
- 相同输入在 Ebox 与 ETAF 中必须一致解释 class、id、状态和结构关系；归一化规则也属于公共契约。
- 样式表及上下文由对应 surface 或组件拥有。允许共享明确只读的值或不可变缓存，不允许不同应用隐式共用一个可变的当前样式上下文。

组件仍是样式边界：父组件规则不自动穿透子组件内部；调用者提供的 slot 内容保留调用者的样式所有权，子组件自有 fallback 保留子组件的所有权。ETAF 负责描述这些事实，ECSS 负责在相应作用域内计算规则。

焦点、禁用、按下和悬停等宿主状态由 Ebox 的交互机制产生，并以统一状态语义影响样式。原生悬停等快速路径可以保留，但必须与声明的公开行为一致，不能成为第二套优先级算法。

## 4. ETAF 到 Ebox 的转换契约

```text
应用状态写入
  → 响应式图只重新运行读取该状态的细粒度绑定（属性、文本、动态区域、键控列表）
  → 绑定通过 Ebox 公共节点操作修改对应的保留节点，并按绘制／文本／布局分类标脏
  → 批次结束时 Ebox 调用 ECSS，在最近的重新布局边界内重算布局，合成受影响的行
  → Ebox 直接改写受影响的 buffer 区段
  → Emacs redisplay
```

- `etaf-view` 和 `etaf-define-component` 在展开时把静态结构与动态部分分开。挂载时每个 Host 创建一个保留 Ebox 节点，此后只运行依赖变化的绑定；ETAF 不先输出 `.ebox` 字符串，也不在更新时生成整棵新树再比较。
- 整个更新只有两种状态表示：响应式状态与 Ebox 保留树（含布局缓存和 buffer 位置）。不存在候选树、代际、快照、局部性证明或发布事务。
- Host 的结构与属性以 Ebox 公共能力为准，不能因旧文档里出现某个名字就新增转发别名或保留无实现的节点类型。
- 属性、文本与子节点变化使用不同的 Ebox 公共节点操作。ETAF 只把变化的值写给所属节点；属性的影响类别、重新布局边界和 buffer 改写范围由 Ebox 负责，ETAF 不因属性影响布局而重建子树。
- 计算阶段（绑定、样式、布局与行合成）只写节点的待提交状态和本次改写列表，不碰 buffer；任一步出错时丢弃这些结果，buffer 与已提交节点保持原样。改写阶段只执行 buffer 原语，不运行用户代码。用户已写入的业务 ref 不随之撤销。
- Component、表达式和 fragment 不应仅为运行时记账而意外产生视觉容器。多根输入确实需要宿主容器时，应明确布局语义，并验证它不会意外改变间距、继承、选择器、命中或身份。
- Component key、Host 身份和样式作用域在转换中保留。ETAF 的组件身份与 Ebox 的宿主身份可以有映射，但不得以易变的 buffer 坐标代替对象身份。
- 保持 Ebox 的独立入口和普通 Elisp 用法。ETAF 所需的通用宿主能力必须经 Ebox 公共接口提供，不能仅藏在 ETAF 的内部模块里。

等价性定义为：在声明支持的宿主能力范围内，ETAF 应用可以由“Ebox 节点 + 普通 Elisp 状态/回调 + Ebox 公共更新操作”表达相同的可观察行为，包括输出、目标选择、焦点、生命周期及公开的失败语义。

这不要求把有状态应用转换成一棵静态树，不要求消灭 ETAF Runtime，也不要求两者有相同的实现、执行步骤或耗时。暂不开发独立源码导出器来证明这种等价性，以公共行为场景对照验收。

## 5. 统一交互路径

区域导航、方向键、编辑状态、Escape 与原生中断、应用绑定和帮助的详细目标统一由[区域导航与键盘交互方案](keyboard-navigation.zh-CN.md)维护。本节规定其共享输入路径和分层边界。

```text
Emacs 输入
  → Ebox 按 buffer 中已写入的节点与 keymap 确定目标、焦点和操作边界
  → 调用绑定的处理器
  → ETAF 在应用状态批处理中执行回调
  → 响应式图只重新运行受影响的绑定，修改对应保留节点
  → 批次结束时 Ebox/ECSS 重算受影响的样式与布局，直接改写受影响的 buffer 区段
  → 后续输入使用已写入 buffer 的目标
```

直接使用 Ebox 时，将 ETAF 状态处理替换为普通 Elisp 控制逻辑即可。统一路径指共享目标权威与提交契约，不要求用一个巨大函数接管所有 Emacs 命令。原生编辑适配器通过明确的边界保留原生事件与编辑过程。

### 5.1 Ebox 必须提供的通用能力

| 能力 | 所需公开行为 |
| --- | --- |
| 几何与图层增量更新 | 通过公共节点操作修改 Box 的 `left/top/width/height`、约束、可见性和层级；只重新合成新旧覆盖的行，保留稳定节点身份和失败时不改写 buffer 的语义 |
| 激活与自定义键鼠操作 | 明确事件来源、目标及所需原生事件信息；一次操作按约定触发一次；普通 keymap 仍可使用 |
| 命中与嵌套边界 | 使用已提交的布局、可见性和所有权；禁用或无回调的控件边界不能意外激活父控件 |
| 焦点 | 稳定目标身份、程序设置与查询、导航顺序、循环策略；更新后保持或明确回退 |
| 输入范围 | 明确 buffer、事件窗口与逻辑焦点的关系；手动移动 point 和多个窗口不能被隐式覆盖 |
| 交互状态 | 以统一事实提供焦点、禁用、悬停等已支持状态，供样式计算及公共观察使用 |
| 手势输入原语 | 针对实际需要提供开始、移动、结束、取消及统一坐标/位移；手势期间目标保持与重排、删除、卸载的行为明确。原语只产生输入事实，不解释为移动窗口、调整大小或最大化 |

先补齐已有 Button、Checkbox、列表等实际需求。需要拖拽或调整几何时，ETAF 将 Ebox 的手势事实接入受控状态更新；不要让 Ebox 解释窗口策略，也不要让 Playground 成为能力提供方。ETAF 仅提供显式的 `:on-press-capture` 祖先钩子供窗口焦点等 Shell 策略使用，不预先实现完整 DOM capture/bubble；若应用需要更通用传播，先定义宿主树关系、传播顺序、停止条件和验收场景，再作为同一契约的扩展。

### 5.2 ETAF 保留的职责

- 把 `:on-*`、禁用和焦点相关声明转换成 Ebox 的公共交互输入。
- 在正确的 Runtime、事件上下文和响应式批处理中调用应用处理器，维护组件生命周期。
- 保留 `on-change`、提交、删除等组件或业务事件，Behavior 与 Action 继续组合应用行为。
- 提供可复用的交互 Behavior，把 Ebox 的手势阶段转换为调用方拥有的受控几何状态；移动、调整大小的约束和取消语义在此层统一，不能复制 Ebox 的布局或命中算法。
- 不再自行扫描所有 Host 判断物理输入目标，不保留第二份权威焦点，不通过独立输入模式重做 Ebox 已提供的分发。

Ebox 负责“激活哪个控件”；复选框值如何改变、如何向表单报告，以及是否触发业务操作，由 ETAF UI 或应用决定。适配所需的引用映射可以存在，但不能复制另一份坐标或目标真相。

### 5.3 一致性与生命周期

- 目标绑定和处理器随所在节点一起写入 buffer 后才生效；批次结束前的中间状态不接收输入。
- 对象移动或列表重排时，焦点和手势跟随稳定身份；对象删除、隐藏、禁用时，遵循明确的回退或取消规则。
- 失败的更新不得改变已显示画面的目标解析；不能出现旧画面调用新处理器、或新画面调用失效处理器的混合状态。
- 卸载、buffer 关闭和相关窗口失效时，释放焦点、手势、订阅与绑定；旧回调不能复活已卸载的应用。
- 显示更新失败不自动等于业务状态、数据库写入或外部副作用回滚。相关接口必须分别说明失败后状态以及重试方式。

## 6. 增量更新与响应式边界

| 层 | 决定什么 | 不应重复实现什么 |
| --- | --- | --- |
| ETAF | 哪个状态依赖、Component、表达式或 Host 需要重新计算 | 重新布局边界、行合成、直接 buffer 写入 |
| Ebox | 节点变化属于绘制、文本还是布局，需要重算到哪个重新布局边界，以及改写哪些 buffer 区段 | 组件状态图、业务 Action |
| ETAF Behavior | 如何把已提交的手势事实转换为调用方拥有的受控位置/尺寸状态，以及约束、取消和生命周期 | Ebox 的命中、布局和 buffer 写入算法；窗口工作区策略 |
| ETAF UI | 如何把 Behavior 组合成可发现、可键盘操作的面板和窗口外壳 | 应用的窗口集合、z-order、最大化/最小化策略和持久化状态 |
| 应用（例如 `etaf-desktop`） | 窗口模型、工作区、层级、焦点策略、最大化/最小化/还原及应用快捷键 | Ebox/ETAF/UI 已经拥有的几何更新、手势分发和通用控件语义 |

应用 ref 与细粒度绑定归 ETAF，保留节点、布局缓存和 buffer 区段归 Ebox。接入时使用明确的求值与失效适配，不把同一业务值同步成两份权威可变状态。Ebox 不承担应用状态管理。

纯业务元数据变化可以不产生物理显示变更；真正显示变化必须经过 Ebox flush。结构变化或越过所有重新布局边界的尺寸变化会扩大重算与改写范围；挂载、视口变化和显式 refit 重绘整个 buffer，相互重叠的改写范围也会合并为整体重绘；flush 报告如实给出策略、节点变化数与改写行数。

高频输入不得默认每次全量扫描全部 Host 或重新排序整个焦点集合。优先复用已提交身份和显示索引；以测量决定增量索引与事件合并策略。允许合并适合合并的连续移动，不能丢失激活、释放、取消等语义关键事件。

性能验收分开记录 Ebox flush（样式、布局、行合成与 buffer 写入）和 Ebox 之外的输入分发、应用与响应式成本。直接 Ebox 与 ETAF 使用相同输出、数据规模和交互序列；记录环境、延迟分布与工作负载，不以布局基准代替交互性能，也不承诺没有框架开销。具体负载、计时边界和通过门槛见第 11.3 节。

## 7. 复杂输入的边界

当前通用交互缺口主要是可复用机制尚不完整，并无证据表明架构无法扩展。但必须逐项验证宿主能力，不能把“任意回调可执行 Elisp”当成完整的输入、拖拽或编辑契约。

### 7.1 文本编辑

应用内直接输入是必需能力。单行输入和多行编辑以 ETAF UI 通用组件提供，像 input/textarea 一样参与应用布局、主题、焦点和生命周期；用户在应用里直接输入、编辑和提交，不跳到 minibuffer、不切走当前应用，也不需要自行打开独立编辑器。minibuffer 可继续用于显式选择的快捷命令，不是表单和消息撰写的默认实现或验收回退。

“原生编辑”只描述内部复用 Emacs 的输入法、光标、选区、撤销与编辑命令，不规定用户必须使用另一种界面。编辑组件可保有专属 buffer 等内部资源，但其显示、焦点、尺寸和清理必须由提供者统一管理，对应用作者暴露组件与值/事件接口；不能要求每个应用手工拼窗格、转发按键或维护编辑区位置。普通输入随所在布局放置，不限于聊天底部的专用窗格。

Ebox 拥有宿主几何、命中、显示发布及编辑区域的写入边界；ETAF 拥有响应式值、宿主适配和生命周期；ETAF UI 拥有输入组件、编辑行为及组合方式。应用只使用 ETAF/ETAF UI 公共接口，定义提交、发送和草稿保存等业务策略。文本只有一个编辑权威，编辑过程与渲染发布不得同时无约束地写同一片内容；每次按键不得重建整页或编辑器，也不得让后台消息刷新破坏输入法组合、光标、选区或撤销历史。

组件必须覆盖单行/多行、占位提示、只读/禁用、受控值同步、修改/提交/取消、原生补全、大小变化和卸载清理。换行与提交按应用提供的键位策略分开；发送失败保留草稿，发送确认不得清除用户等待期间继续输入的新文本。外部值更新、焦点切换和卸载的行为须有明确契约及回归，不用捕获所有按键的自制编辑器替代 Emacs 编辑能力。

输入会话机制已在 Ebox 与 ETAF 落地，作为应用内原地编辑的底层出口。Ebox 的 `ebox-input-begin`、`ebox-input-text`、`ebox-input-end` 与 `ebox-input-active-p` 在隐藏编辑 buffer 中用原生命令、undo 与输入法编辑 text node 的值，节点保持布局并即时显示每次编辑，flush 不因会话而暂停；ETAF 以 `etaf-input-begin`、`etaf-input-text`、`etaf-input-end`、`etaf-input-active-p` 包装，组件在 `:on-change` 中把值同步进状态，回写同一值不产生效果。会话不保存应用值；输入面是应用布局内的已挂载 buffer，frame 不作为输入面。

原地输入组件的公开能力、编辑退出规则及键盘迁移差距见[键盘交互方案的实现状态](keyboard-navigation.zh-CN.md#10-实现状态与交付边界)。公共组件、消费应用与中文输入法、选区、撤销、后台更新及提交后发布应共同完成 GUI 验收，不能用底层会话或应用专用实现代替完整工作流。

### 7.2 拖拽与原生事件

Ebox 的 `ebox-keymap-create :drag` 提供共享的开始、移动、结束和取消输入原语，复用已提交目标与焦点的身份解析，在重排后保留原控件。它只报告阶段、坐标和位移，几何变化通过公共节点操作写入；不保存窗口状态，也不实现“拖动窗口”或“调整窗口大小”。ETAF 的 `:on-drag` 以及可复用 Behavior 将每个阶段接入普通响应式批处理，按调用方拥有的状态更新位置或尺寸。移动和释放完成更新与 redisplay 后才读取下一事件，释放位置参与最后一次更新。

拖拽还报告 `edge` 意图阶段：已移动的手势停在窗口边缘带内时，Ebox 按固定节奏给出贴住的边缘（`:edges`），但不滚动任何内容。视口、滚动步长以及内容锚定目标如何跟随滚动仍归应用所有，ETAF 只把阶段原样分派给 `:on-drag`。Escape 在锁定与普通拖拽中都产生 `quit` 取消并消费该键。

底层手势只提供目标归属、统一坐标、位移、阶段和清理；位置与尺寸仍通过普通布局输入更新。Ebox 不包含窗口管理语义。ETAF 提供可组合的拖动/调整大小 Behavior 和状态更新约束；ETAF UI 提供标题栏、边缘手柄及可移动/可调整大小的面板外壳。最大化、最小化、还原矩形、吸附与窗口层级属于 `etaf-desktop` 或其他应用的状态和策略。独立 Ebox 消费者使用普通 Elisp 状态，ETAF 消费者使用同一手势驱动响应式状态。

公共场景必须覆盖中途更新、重排、禁用、移除、卸载、窗口切换、移出窗口及无关输入保留；各层的真实 GUI 鼠标路径和延迟仍须单独验收。`ebox-playground` 只验证 Ebox 原语，`etaf-playground` 只验证框架组合；它们不拥有窗口策略。完整桌面工作流由独立的 `etaf-desktop` 应用验收。

基于 Emacs keymap、鼠标事件和命令循环实现，避免再造事件循环。仅在原生手势确需跟踪时使用有界的跟踪过程，并正确处理退出和无关输入。终端、GUI、跨窗口和跨 frame 的支持范围分别验收，不从单个演示推断全部支持。

## 8. ETAF 组件与公共 API 的重构要求

组件目录纪律：同一功能只维护一个基础组件，变体通过 props 特化或组合（例如单行/多行由 `:rows` 区分），禁止为同一功能新增同义组件。

ETAF 保留组件、单向输入、实例状态、响应式依赖和自动清理这些基础。下一轮重构先修正容易误用的语义，再简化日常写法，随后补齐复杂应用能力。不能以增加概念、缩短名称或机械减少 API 数量代替易用性改进。

### 8.1 概念分层与主要写法

| 概念 | 面向用户的定位与约束 |
| --- | --- |
| View / Component | 界面描述与复用的基础；`:view` 是主要声明写法，`:render` 和 `etaf-node` 是进阶的普通 Elisp/程序构造入口，共用同一套语义 |
| props / slots | props 表达输入，slots 表达内容组合；沿用组件和 slot 的既定所有权，不再新增另一套传值或内容模型 |
| ref / computed | ref 表达可变状态，computed 表达派生值；保留显式读取与浅响应式规则 |
| `:on-press` / `:on-change` | 普通交互的默认入口；明确区分宿主激活与组件值改变，简单回调不要求注册 Action |
| `etaf-on-mounted` 等 | 生命周期回调，作为组件生命周期的一部分说明，不另立一个“On”概念 |
| watch / watch-effect | 处理外部同步与副作用；派生显示值优先使用 computed，不能靠多份可变状态互相监听来维持一致 |
| Context | 跨层共享服务、主题或模型；简单父子输入仍用 props，slot 上下文规则沿用既定契约 |
| Behavior | 进阶的宿主附着能力，具有安装、更新、清理边界；不承担所有逻辑复用 |
| Action | 可选的命名业务命令边界，供多个入口复用及统一观察；业务函数本身仍可独立调用和测试 |
| Resource / Data | Resource 表达加载生命周期；Data 在同一加载基础上组合集合、查询、分页、选择与变更后的刷新 |

入门示例集中在组件、props/slots、状态和事件回调。保留 `expr` 对结构与普通 Elisp 表达式的区分；现有条件、循环指令继续转换到同一条路径，不增加多套等价的控制流或组件语法。复杂能力按真实任务渐进引入，不让一个基础计数器承担展示全部概念的职责。

### 8.2 props、回调与输入契约

- 组件渲染产生的普通回调必须能够直接引用该次已提交的 props，并在延后调用时取得正确的词法快照。不能要求调用者了解隐式动态上下文，额外加一层 `let` 才能避免读到 nil。
- setup 中长期存在的 computed/watch 需要明确的、可跟踪的只读 props 来源。props 更新后，相关派生值必须更新；一次初始化使用的初始值与持续读取的属性来源必须能区分。
- 事件中的已提交属性快照与显式传入的实时 ref 是不同契约。后者继续保留引用身份；不能把它悄悄冻结成快照，或为实现快照而任意深复制外部资源。
- 支持组件默认参数，并区分未传入与显式传 nil；规定默认表达式的求值时机和可变默认值的所有权，避免组件实例意外共享状态。
- 按实际需要提供输入校验。错误至少指出组件、属性、收到的值和期望值，不能只留下底层类型错误或无上下文的内部路径。
- 样式、class、禁用和事件透传继续有明确的合并规则，保留内部动作与宿主语义保护。业务回调、宿主事件和追加观察回调必须在组件接口中可区分，不能依靠包装层次猜测覆盖或追加顺序。

必须明确列出真正支持的宿主事件、参数和触发时机。能够接受任意 `:on-*` 名称，只代表声明或回调可被保存，不能据此宣称已接入对应的原生键鼠事件。

### 8.3 实例状态、引用与受控绑定

- 保留 setup 一次初始化、视图后续计算的生命周期。提供一次声明的实例命名绑定，让视图和处理器能够直接引用稳定句柄，减少反复装入 plist、调用 `etaf-state` 再逐项拆包的样板。
- 命名绑定采用已实现的 `:bindings ((name initializer) ...)`：按顺序初始化一次，视图和回调直接使用保留值，可选 setup 负责初始化工作。具体契约见 [ETAF 入口](https://github.com/emacs-taf/etaf/blob/main/etaf.el)；保持身份、闭包、组件重排、失败和卸载的公共验收。普通应用使用命名绑定，原有 `etaf-state` 仅用于没有命名绑定的进阶 opaque setup 用法。
- `etaf-ref`、`etaf-value` 与 `etaf-computed` 保持明确含义。原地修改 ref 内的 plist、向量等不被自动视为响应式写入；`etaf-update-value` 将普通函数返回的新值交给现有写入路径，不通过隐藏深层代理改变普通 Elisp 数据语义。更新函数不得修改旧值或执行外部副作用；函数失败保留旧值，写入后的显示失败不撤销业务值。
- 组件内部定位采用实例局部引用或稳定句柄。两个实例可以各自定位同名内部控件而不冲突；对外地址通过明确接口暴露。普通按钮和普通组件组合默认不需要手写 `:ref` 或生成唯一符号。
- 列表 key、宿主引用和状态 ref 分别负责保留身份、定位和业务值，不得混为一套对象。通用定位与焦点机制最终仍由 Ebox 提供，ETAF 只承担组件实例到宿主身份的映射。
- 保留受控控件的“当前值 + 修改回调”模型。UI 的 Checkbox、NumberInput 已通过普通 `:bind` 属性组合现有值与回调，直接读写调用者的 ref，不产生另一份控件权威状态。非 nil 绑定与显式值或 `:on-change` 冲突，追加 `:on-press` 仍遵循原有事件顺序；业务转换与数据操作使用显式回调。详细契约由 UI 入口和手册维护，后续输入控件沿用同一规则。

### 8.4 逻辑复用、Behavior 与 Action

查询、筛选、表单状态和业务操作优先用普通 Elisp 函数组合，必要的 watch、资源和清理归调用者的组件 Scope。不要为了复用几行逻辑就创建额外组件实例或 Behavior。

Behavior 保留宿主附着与资源生命周期契约。构造函数可以是普通函数；`etaf-define-behavior` 只作为便利写法，不作为另一门语言或入门必需概念。必须能通过公共接口获得实际需要的宿主上下文，明确配置变化、重新安装和清理的时机，并遵守 Ebox 统一交互路径。

Action 用于有名字的共享业务操作和命令观察。简单本地状态修改直接使用回调；不要求普通业务函数接受 Runtime 或依赖全局注册。跨入口分发确需命名时，再使用 Action 边界，并明确名称作用域、重定义和多应用行为。禁止在组件业务逻辑中手工管理提交后的回调缓存或内部调度状态。

### 8.5 异步 Resource 与 Data

Resource 和 Data 必须共用一套加载生命周期，支持同步加载及适合 Emacs 的异步适配。保留 Data 的集合、分页和选择职责，不将两者合成含义不明的万能数据对象，也不为此立即新增通用异步包。

公共契约至少覆盖：

- 首次加载、未启动、成功、失败、后台刷新以及是否保留旧结果的明确状态；同步与异步入口采用一致的状态和错误约定。
- 连续搜索或重载时，只发布当前有效请求的结果；旧请求晚到、重复完成或取消后完成均不能覆盖新结果。
- 能取消的外部任务执行取消；不能取消时仍使结果失效。组件卸载后不得更新或复活界面，相关回调和资源必须释放。
- 超时、重试与外部错误可观察；用户不需要自行拼接请求编号、存活标志和清理流程。
- 数据写入与刷新分别报告结果。写入已成功、刷新或渲染失败时，重试不能盲目重放写入，沿用已有发布与外部副作用边界。
- 取消等待或超时不表示外部写入已撤销。结果未知时必须区别于明确失败；自动重试写入需要提供方的幂等或结果核对契约，不能由通用加载器承诺任意外部操作恰好执行一次。

具体异步句柄及适配签名在提供方接口设计时确定，优先使用 Emacs 原生异步能力。原型必须实际演示乱序完成、取消与卸载；不能只通过同步 loader 或一个立即返回的演示宣称支持异步。

### 8.6 表单、控件与错误恢复

ETAF UI 按参考应用需要补充文本输入、选择器、菜单和对话框等控件，并组合表单草稿、校验、修改状态、保存与取消。原生文本编辑和物理焦点按第 7 节的 Ebox 边界实现；这些产品控件不成为 ETAF 核心的另一组 Host 类型。

buffer 内的 Popover、下拉菜单和模态框复用 Ebox 的根浮层、锚点定位、遮挡命中与
子树焦点导航；UI 负责展示、关闭及键盘策略，应用负责表单值和提交。浮层可组合
普通组件与 slot，关闭后释放局部按键并通过共享焦点恢复有效入口。可移动面板、
可调宽分栏和窗口外壳由 ETAF UI 组合 ETAF Behavior 与 Ebox 几何更新原语；UI
不拥有窗口集合、工作区、z-order 或最大化/最小化策略。完整的窗口管理器（例如
`etaf-desktop`）属于应用层，沿用这些公共组件并拥有自己的窗口状态。具体已支持
组件以 UI 入口为准。

模态背景是共享视觉契约：打开设置、帮助等居中弹窗，以及抽屉、启动器和切换器时，
应用已绘制的画面必须保留，由共享压暗层统一调暗，文字与图片都不丢失；不得改用
不透明色覆盖，也不得由某个应用自行复制一套压暗算法。Ebox 提供该合成能力
（`:backdrop-filter`），etaf-ui 的浮层组件默认使用它；压暗层同时承担对下层控件的
遮挡命中，键盘仍留在模态子树内。点击模态框外的遮罩必须请求关闭当前模态框，
不穿透到背景业务控件；点击框内不关闭。关闭后恢复有效焦点和滚动位置，保留业务状态。
只有调用方明确要求完全不绘制背景时才使用无背景浮层，其外部点击策略由调用方提供。
快捷键帮助复用这一基础交互，不另建 Emacs window、帮助 buffer 或应用 Runtime；
详细键盘与帮助规则见[区域导航与键盘交互方案](keyboard-navigation.zh-CN.md#7-按键帮助与可发现性)。

大数据列表按实际测量增加虚拟化；稳定 key、局部行更新或分页本身不能作为虚拟化已经实现的证明。控件应表达数据和交互意图，通用宿主定位、提交一致性及回调生命周期由框架承担。

ETAF 必须提供持续存在的组件渲染错误边界，使某一区域失败后能显示该区域的错误和重试入口，其他区域继续可用。边界在同一次更新中把失败区域替换为错误内容，不能先破坏旧画面再尝试补救。

当前 `etaf-error-boundary-run` 只包住一次同步函数执行，不是上述持续边界。重构时明确其定位，若被新接口替代则迁移调用者并删除旧入口，不保留误导性兼容包装。渲染错误、事件错误、异步加载错误、边界自身错误和外部写入失败各自有明确处理范围，不能全部吞进一个捕获器。

### 8.7 公共接口完整性与开发体验

每个公开对象必须能通过公共入口完成创建、使用、更新、错误处理和释放，或明确由哪个公开所有者自动释放。不能公开创建入口，却要求调用者使用私有函数完成清理；返回的上下文也必须有足够的公共查询能力。

effect scope 的创建、进入、清理注册和停止接口已完整公开，独立调用方可以通过公共接口完成整个生命周期。Behavior 安装上下文已有公开快照查询，明确区分安装事实与已提交 Host 状态。`etaf-data-error` 和 `etaf-resource-error` 的读取函数与同名错误条件已分别记录并验证。根据实际调用场景设计完整契约，再同步入口、检查器和验收；不要仅为保留内部测试而扩大公开面。

公共入口按应用开发、扩展集成、诊断工具分组，仍是同一个权威 API 清单。性能和 Runtime 查询不应淹没入门接口；不要为了减少记录数量机械删除有实际调用者的能力，或公开整个内部结构代替稳定查询。

补充组件定义跳转、props 补全及带组件路径和可用源位置的错误信息。开发时重定义与重新挂载应有明确流程，说明何时保留或重置状态，不强迫用户绕过注册器或了解内部开关。已有性能记录继续负责测量，不能代替这些基本开发工具。

### 8.8 应用数据的存储策略

应用自有、会增长且需要增删改查的持久数据默认使用 `etaf-db`（当前 SQLite）通过 Data
Source/Controller 契约存取；后端权威数据不复制为第二权威，只落本地派生值（索引、进度）；
远程列表先用 `etaf-list-cache` 展示并在后台校验，缓存不得作为唯一答案。

存储模式按已实现的契约为准：元数据与正文分表，使列表查询不必载入大字段；写入按界面
需要设置分页，批量导入使用 `etaf-data-mutate-many` 只对账一次，具备 `:mutate-batch` 的
源在一个事务内整批提交；schema 演进默认由 `etaf-sqlite-initialize` 补齐新增的可空列，
主键或非空列变更必须显式迁移并给出可读错误。

这不是要求所有数据都必须入库：微小配置与可丢弃的内存缓存不承载该默认。

| UI 组合 | 参考应用所需的文本输入、状态选择、行操作菜单、确认对话框及现有基础控件；补齐可组合的 buffer 内 Popover、下拉菜单、模态框、可移动面板和可调整大小的窗口外壳；键盘可达、禁用保护与关闭后焦点恢复 | 文本输入与可搜索列表可复用 Emacs 原生界面；不要求浏览器式浮层系统或一整套控件目录；工作区与桌面窗口策略由应用包实现 |
| 拖拽与几何行为 | Ebox 提供几何增量发布和手势输入原语；ETAF 提供受控的拖动/调整大小 Behavior；ETAF UI 组合可发现的面板外壳 | 移出目标窗口、取消、目标或窗口失效必须安全结束；跨窗口、跨 frame 拖放与终端鼠标拖动暂不承诺；最大化、最小化、还原和 z-order 不下沉到提供方 |
| `etaf-desktop` 应用 | 以 ETAF/ETAF UI 公共接口实现独立 Emacs 桌面管理器，拥有 Manifest/Registry、实例生命周期、窗口模型、工作区、浮动/tiling/master-stack/monocle 布局树、会话和窗口操作策略；提供可运行的多窗口、层级、移动、调整大小、最大化、最小化、还原、启动器、切换器和错误隔离流程 | 不把应用状态、窗口策略或第二套前端交互加入 Ebox、ETAF 核心或 UI；不把 Playground 的示例状态当成公共 API；前端组件与 Behavior 必须复用 ETAF/ETAF UI 公共接口 |
| 文本编辑 | 交付应用布局内直接编辑的通用单行/多行组件，支持中文输入、光标、选区、撤销、补全、受控值同步、提交和取消；迁移 `etaf-pi` 到公共组件 | 编辑资源与发布边界按第 7.1 节验证；minibuffer、切走应用或应用自行拼装输入窗格均不能替代组件验收；任意富文本所见即所得编辑不属于基础交付 |
| 数据规模 | 参考应用（待重建）的 100 条任务、每页 10 条，以及 Research Shelf 的 256 条记录、每页 12 条满足正确性和性能门槛 | 不宣称支持无限数据量；虚拟化仅在目标负载测量表明需要时加入，分页不算虚拟化 |
| 开发体验 | 组件定义跳转、props 补全、带组件上下文及可用源位置的错误；明确重定义后的重挂载与状态重置流程 | 默认允许重挂载重置状态；自动保留任意热更新状态、完整可视化调试器不属于基础交付 |
| 生态一致性 | 消费者、示例、安装入口、包元数据和已实现文档同步；数据库后端包统一为 `etaf-db`，当前 SQLite 后端复用核心 Data Source 契约，工作区与两端远程引用一致 | 不保留旧入口的兼容包装；不因通用定位声称尚未实现的后端已受支持 |

原型允许确定尚未冻结的 API 形式，但不能放宽已经确定的行为、所有权和清理契约。原型结论及其设计依据维护在所属契约中，未交付能力不能进入已支持 API 清单。

### 10.2 验收环境与支持范围

- 保持现有包声明的最低 Emacs 版本；ETAF 生态集成至少在 Emacs 29.1 和交付时使用的 Emacs 版本完成公共行为与安装验证。ECSS 独立包保留自己的版本约定，不能随上层无依据提高要求。
- GUI 基础验收使用当前 macOS 图形 Emacs 环境，记录准确版本与构建、字体、缩放、窗口尺寸和后端。当前 Emacs 31.1 开发构建的结果不能代替 Emacs 29.1 兼容性验证，也不能外推到其他操作系统。
- 终端单独验证键盘导航、激活、原生文本输入和清理；不要求与 GUI 像素排版完全一致。其他系统的 GUI、系统间拖放及跨 frame 手势不在本轮认证范围，已有公开支持不得静默撤销。
- 可选原生加速器（如 EKP）启用、禁用和不可用时分别验证提供方承诺的行为。Ebox 的布局与更新没有原生后端，性能门禁直接衡量其 Elisp 路径。SQLite 验收使用具备 SQLite 支持的 Emacs 和独立临时数据库。

缺少某个必需环境的实测结果即表示该项未验证，不能用跳过检查或改写最低版本代替完成。

### 10.3 依赖顺序

以下顺序约束提供方与消费者的落地关系，各项以对应的可观察结果作为退出条件。核心架构以通用抽象、组合复用、合理的职责归属、清晰的公共接口及跨模块配合为完成标准；渲染、布局、响应式更新和宿主交互通过这些能力支撑复杂应用。提供方必须能独立使用，消费者通过公共契约组合其能力。组件和示例用于检验整个数据流，不以控件数量、额外交互细节或异常测试数量代替核心架构的完成。先完成这些路径及复杂应用的正常读写流程，再扩展故障隔离、回滚与重试；整体交付仍须满足功能、渲染和性能验收。

1. **修正 ETAF 基础语义与公共接口完整性。** 优先处理 props 回调、派生依赖、默认参数、实例局部引用和生命周期出口。退出条件是公共场景能够完成创建到清理的全过程，重复组件与失败发布不会读错属性或目标。
2. **统一样式基础。** ECSS/Ebox 确定规则输入和作用域公共接口，随后迁移 ETAF、UI 与 Playground。退出条件是等价选择器、层叠、主题和组件边界场景通过，旧匹配器与包装语法及调用者一并删除。
3. **补齐基础宿主交互。** Ebox 独立实现现有控件所需的激活、禁用边界、焦点与更新保持。退出条件是无需加载 ETAF 即可通过对应公共行为场景。
4. **统一 ETAF 接入与发布一致性。** 将交互声明转换到 Ebox，保留应用批处理与生命周期。退出条件是两种写法的行为对照通过，重排、隐藏/删除、多应用、失败和卸载场景一致，旧目标扫描、焦点权威与重复分发被删除。
5. **简化应用写法。** 验证命名状态绑定、普通函数组合、受控绑定简写和分层入门接口。退出条件是常见组件显著减少重复装箱、拆箱和绑定代码，保持状态、闭包与更新语义，不引入第二套组件或控件状态模型。
6. **补齐复杂应用正常流程。** 实现 Resource/Data 共用的异步生命周期和表单组合。退出条件是列表、搜索、分页、选择、编辑、校验与异步保存通过公共契约连成可用的应用，并满足对应渲染与交互性能门槛。
7. **完成宿主与开发能力。** 按第 10.1 节交付几何增量更新、共享手势、应用内单行/多行编辑组件，先迁移 `etaf-pi` 再用于 `etaf-telega`，验证规定数据规模，补充组件跳转、补全与错误定位。每项以自己的公共、GUI 或性能验收结束；未验证的宿主能力不得标为支持。
8. **交付 ETAF UI 的通用面板能力。** 在 ETAF Behavior 稳定后，提供可移动、可调整大小的面板/窗口外壳和可访问的标题栏、手柄与操作按钮；退出条件是组件只消费提供方公共接口，不维护第二套布局、命中或焦点真相。
9. **交付 `etaf-desktop` 应用。** 以工作区记录的 ETAF 与 ETAF UI revision 为依赖，独立实现窗口模型、工作区、层级、焦点、移动、调整大小、最大化、最小化和还原；退出条件是多窗口完整流程通过公共、GUI 与性能验收，且 Ebox/ETAF/UI 没有新增应用策略。
10. **补充错误恢复。** 核心正常路径通过后，补齐持续组件错误边界及参考应用的失败恢复。退出条件是取消、乱序完成和重试通过公共契约工作，写入后刷新失败不会重复写入。
11. **完成生态迁移。** 在对应边界变更时同步入口说明、手册、示例和依赖；完成 `etaf-db` 数据库后端包入口、桌面应用入口与 Playground 依赖整理。退出条件是安装、独立使用和集成组合均可复现，没有遗留兼容入口或失实文档。

迁移不能以长期保留两套语义作为完成状态。消费者必须使用已落地的提供方公共接口，最终集成版本必须能由工作区记录的 revision 复现。

### 11.1 各层公共契约

测试以输入、输出、错误及生命周期的可观察结果为准。下面是开发所需场景，不是已经通过的测试清单；各包的 `tests/acceptance.json` 只登记真正落地的测试。

| 场景 | 必须观察到的结果 |

| 独立使用 | ECSS、EKP 不加载上层；Ebox 无 ETAF 可渲染并交互；ETAF 不依赖 UI、数据库或 Playground 才能启动 |

| 作用域与隔离 | 父子组件、slot 与 fallback 保持声明的边界；两个应用的主题、样式和状态不互相污染 |

| 焦点 | 导航顺序与循环策略正确；重排跟随身份，删除/隐藏/禁用后按契约回退；手动 point 和事件窗口行为明确 |

| 瞬态界面借位 | 活动的 minibuffer、补全弹窗或 echo area 借用窗口行数时，应用保持已提交的布局与视口，不按借用高度重排（统一判定 `etaf-transient-space-borrowed-p`）；借用结束或窗口真实变化时继续跟随真实几何，借用期间发生的 frame 变化在结束时应用 |
| 发布失败 | 公开输入触发的失败保留上一个成功画面和匹配的交互语义；业务副作用按各自契约处理 |
| 生命周期 | 挂载、替换、卸载、重新挂载和 buffer 关闭后，无旧回调或订阅影响新应用 |
| 拖拽 | 更新时不丢失目标；释放、取消、目标删除及窗口失效正确结束手势；无关输入按契约保留；边缘意图只报告边缘，滚动由应用拥有 |
| 交互 Behavior | ETAF 的拖动/调整大小 Behavior 将 Ebox 阶段和位移转换为调用方拥有的几何状态，约束、取消、卸载和重排行为一致；不复制 Ebox 命中或布局算法 |
| UI 面板 | ETAF UI 的可移动/可调整大小面板只组合 ETAF Behavior 和 Ebox 更新；键盘、指针、禁用、焦点恢复与错误清理可观察且无第二套目标真相 |
| 桌面应用 | `etaf-desktop` 的多窗口可创建、移动、调整大小、置顶、最大化、最小化、还原和关闭；窗口状态只在应用拥有，多个工作区和实例互不污染 |
| 应用内编辑 | 用户直接在应用布局中的单行/多行组件编辑，不打开 minibuffer 或切走应用；中文组合输入、光标、选区、撤销、补全与提交/取消可用；后台内容更新、外部值同步、resize、焦点切换及卸载不破坏编辑状态；验证发送失败留稿、确认不误清新文本以及同屏多个输入实例隔离 |
| 性能 | 第 11.3 节规定的负载与计时边界全部通过；直接 Ebox 与 ETAF 的对照使用相同输出和交互语义 |
| props 与闭包 | 直接引用 prop 的回调使用已提交值；更新后使用新值，失败的更新不能替换它；显式实时 ref 保留原有引用契约 |
| 派生输入与默认值 | 受跟踪的 props 变化使 computed/watch 正确更新；初始快照不被误当持续依赖；缺省与显式 nil、多个实例的默认值按契约区分 |
| 组件复用与状态 | 同一组件多个实例的局部引用不冲突；命名状态绑定在更新、重排和卸载时按约定保留或清理；公开替换更新能够刷新显示 |
| 受控绑定与组合 | 绑定简写与手写值/回调行为一致，没有第二份状态；普通函数复用逻辑不要求 Action 或 Behavior，显式组合的回调按约定执行 |
| 异步加载 | 人为安排乱序结果、取消、超时和卸载，旧结果不能覆盖当前结果；状态和错误可读，不能真正取消的任务也不能重新激活已失效界面 |
| 表单与写入恢复 | 草稿、校验、修改状态、保存和取消一致；写入成功而刷新失败时，恢复不重复提交同一写入 |
| 组件错误边界 | 子区域后续渲染失败能进入其 fallback 并重试，其他区域继续可用；事件、异步及边界自身错误按各自契约处理 |
| API 与开发工具 | 公开对象可完整创建、查询和释放；错误条件与错误值读取有正确说明；支持的组件跳转、props 补全和错误定位可通过用户操作验证 |

只维护公共 API 行为测试。不要修改私有 helper 测试以适配重构，不通过读取内部结构、源码文本、调用次数、猴子补丁或提升内部符号来保住旧测试。跨层对照使用各包的公开入口；故障场景也必须从支持的输入、错误或生命周期进入。

各阶段运行相关公共验收和结构检查，完成包变更前运行 `make check`；跨包完成后运行工作区检查及受影响消费者检查。GUI 与性能单独验收，批处理通过不等于它们通过。

### 11.2 参考应用与完整用户流程

参考应用位置待重建：原 Task Workbench（`etaf-playground/examples/task-workbench.el`）已于 2026-10-07 移除，代码保留在仓库历史中。新参考应用应具备列表、筛选、选择、主题、异步读写，以及标题／状态草稿、空值校验、保存／取消、切换确认和行菜单。菜单通过 UI 的原生输入边界提供编辑与已完成任务的确认删除。数据服务可安排延迟、乱序、失败、取消、超时和丢失写入回执，并通过现有公共 Data 接口完成只读恢复；持续组件错误边界仍待交付。以下完整流程共同构成参考应用的退出条件，已有单项场景不能替代整体验收。

参考应用（待重建）使用每实例独立的 100 条任务、每页 10 条数据，保留稳定任务身份；标题和完成状态构成最小编辑表单。验收数据源通过支持的适配接口安排延迟、失败和完成顺序，使用真实 Emacs 定时器或进程异步完成，不能靠阻塞等待或立即返回伪装异步。每条流程使用明确的初始数据；不得依赖上一条测试的偶然残留状态。

| 用户流程 | 必须观察到的结果 |
| --- | --- |
| 打开与实例隔离 | 同时打开两个工作台，各显示 100 条、10 页；一个实例的选择、查询、主题、草稿和错误不改变另一个；初次异步加载结束前有明确加载状态 |
| 键盘与鼠标 | 键盘导航、RET 和真实鼠标分别可选择任务、切换完成状态、翻页和执行操作；每次激活只生效一次；禁用操作不会执行；过滤或删除焦点行后仍可继续导航 |
| 搜索与乱序 | 先查“接口”再查“文档”，安排后一个请求先完成；只显示“文档”结果，前一个晚到也不覆盖；清空查询回到完整集合且页码有效；加载中其他控件仍能操作 |
| 编辑与校验 | 修改标题或状态只改变草稿并标记已修改；空白标题不能保存且错误定位到字段；明确执行放弃修改才恢复已提交值并清除修改状态；编辑退出遵循[键盘交互方案](keyboard-navigation.zh-CN.md)，切换任务前明确处理未提交草稿，取消切换保留当前草稿 |
| 菜单、对话框与原生输入 | 行操作菜单可打开编辑或删除；未完成任务的删除操作保持禁用；取消确认不改数据，确认只删除一次；关闭菜单、对话框或原生编辑后焦点回到有效入口；中文输入、选择、撤销和取消不破坏表单 |
| 异步保存与恢复 | 保存期间显示状态且阻止重复提交；已知写入失败保留草稿并可重试；写入成功而刷新失败明确显示两种结果，再试只刷新，已提交记录不重复写入；结果未知时按第 8.5 节处理 |
| 取消、超时与卸载 | 搜索取消或超时后可重试；关闭正在加载或保存的工作台，再让旧操作完成，不得重开界面或改变另一个实例；已发生的外部写入不被显示卸载伪装成撤销 |
| 持续错误边界 | 通过示例组件的公开输入使详情区域在后续更新时渲染失败；该区域显示 fallback，列表与另一实例继续可用；修正输入并重试恢复详情；事件和加载错误按各自契约报告 |
| 重排、布局与增量 | 行重排后选择和焦点跟随任务身份；主题变化、窗口收窄再放宽后命中和焦点位置正确，必要控件可达；同状态的增量输出与重新挂载输出等价 |
| 清理与再次打开 | 卸载及关闭 buffer 均释放所属资源；重新打开得到约定的独立初始实例；旧快捷键、订阅或延迟回调不重复触发业务动作 |

编辑和保存至少各有一个可发现的键盘入口，与鼠标操作调用同一业务逻辑。原生输入、对话框或异步操作不能要求应用作者自己接管 Ebox 的命中或焦点系统。

`etaf-desktop` 是独立的应用级验收对象，不改变 Task Workbench 作为数据应用参考的职责。它使用 ETAF UI 的面板/窗口外壳、任务栏/启动器/切换器/分割器和 ETAF 的交互 Behavior，在一个 Emacs buffer 或明确声明的 surface 内管理多个文本盒子。验收必须观察：窗口可以通过标题栏移动、通过边缘或角落调整大小；点击或键盘命令更新活动窗口和 z-order；最大化保存并恢复原矩形，最小化从工作区移除并可恢复；浮动与平铺模式切换、分割比例调整、工作区切换、启动器和切换器都通过公共 UI 回调工作；关闭、卸载、buffer 失效和更新失败不会留下旧手势、焦点或回调。窗口状态、工作区、布局树和快捷键属于该应用，不能反向成为 Ebox、ETAF 或 ETAF UI 的隐式全局状态。

桌面窗口标题、应用内容与设置默认继承用户当前 Emacs 标准字体；标题通过加粗和颜色强调，不能默认增大字号。共享物理文本行的盒子不得因局部字体、图标或后备字形而撑高相邻盒子。Ebox 负责定位内容的规范字体行高边界，UI 与应用负责选择适合宿主字体的默认标记；任意调用方 face 或字体集回退仍须实测。GUI 验收在用户实际配置中记录标准行高，并检查焦点切换、设置页切换和布局交互后的物理行高与相邻窗口像素位置；只比较字号或模型矩形不能证明画面稳定。

Research Shelf 保留为 SQLite 集成与固定性能负载，使用 256 条记录、每页 12 条和临时数据库；需验证成功写入在关闭后重新打开同一数据库仍存在，刷新重试不重复写入。它不承担另一套框架概念或重复的参考应用职责。直接 Ebox 的对照沿用 Ebox Playground：覆盖相同的激活、焦点、重排、禁用、取消、卸载及拖拽行为，普通 Elisp 负责对照应用的业务状态。

易用性验收以相同业务功能比较重构前后的状态/回调样板和必需概念，并检查最终应用代码：普通表单不依赖 Action/Behavior 才能工作；不反复打包/拆包 setup 状态；不手工生成实例内部唯一符号、修补 props 闭包、维护过期请求编号或提交后回调缓存。使用公开组件、状态和事件即可完成基础流程；异步和错误恢复按需求渐进引入。减少代码不能通过省略校验、清理、取消或错误处理达到。

### 11.3 性能门槛与证据边界

50 ms 是本生态对指定负载和验收环境的交互目标，不是 Emacs 或其他机器上的通用性能保证。功能正确、批处理耗时、前台 GUI 耗时和分层诊断分别验收；任何一项的成绩不能代替另一项。

| 负载 | 计时与样本 | 通过条件 |
| --- | --- | --- |
| Research Shelf 批处理 | 使用 `etaf-playground/benchmarks/performance-scenarios.el` 和工作区 `scripts/performance.py`；256 条、12 条/页，初始 viewport 宽 1413 像素、高 62 行。当前注册选行、主题、查询、分页和 resize；初始化挂载、写入、焦点、重载及 resize 后交互仍须补齐，注册场景通过不能代替这些未覆盖目标 | 三组独立初始化，每场景每组 5 次预热、30 次正式样本，各场景 p95 和 max 均 ≤ 50 ms；注册场景可有更严格预算，数据结果同时正确 |
| 参考应用前台 GUI（待重建） | 100 条、10 条/页；测量选行、状态切换、分页、提交查询、主题、打开/取消编辑、校验、保存启动及异步完成后的发布；以动作回调开始至对应发布完成并强制 redisplay 返回为边界 | 三组独立初始化的实例和数据源；每项每组记录 5 次预热、30 次正式样本，正式样本 p95 和 max 均 ≤ 50 ms；宽、窄两种固定窗口状态均通过，尺寸变化后的交互也满足门槛 |
| Research Shelf 前台 GUI | 相同 256 条、12 条/页，至少覆盖选行、主题、查询、分页、写入及 resize 后交互；相同前台计时边界 | 同样三组独立初始化、每项每组 5 次预热和 30 次正式样本，p95 和 max 均 ≤ 50 ms；不能引用批处理结果充当前台样本 |
| Ebox / ETAF 对照 | 使用相同渲染节点规模、可见输出、字体、viewport、后端与动作序列；从参考应用（待重建）提取选行、状态切换和主题更新的等价公开用例，分别以直接 Ebox 和 ETAF 实现 | 两者行为一致且分别满足相同 GUI 门槛；报告两者分布与差值，不预设零框架开销，不以不同工作量比较优劣 |
| `etaf-desktop` 前台 GUI | 在固定窗口尺寸和字体下挂载至少四个文本窗口，轮换执行移动、边缘/角落调整大小、置顶、最大化、最小化、还原和关闭；从应用命令开始至对应几何发布和强制 redisplay 返回计时，另行检查焦点、层级和矩形恢复 | 三组独立初始化、每组 5 次预热和 30 次正式样本；本地操作正式样本 p95 和 max ≤ 50 ms，且每项均通过几何、焦点、层级和生命周期正确性检查；首次挂载和用户思考时间单独报告 |
| 分层诊断与观测开销 | 同一负载另行记录 Ebox flush 耗时、策略与改写行数，Ebox 之外的输入分发、应用与响应式耗时，以及 GC；诊断采样与正式延迟采样分开 | 每类操作能关联到其中的全部 flush；现有 Research Shelf trace 开销比较保持 `abs(p50) ≤ 2 ms` 且 `p95 ≤ 2 ms`；这项 2 ms 限制只约束观测开销，不是 ETAF 相对 Ebox 的开销预算 |
| 细粒度引擎门禁 | `python3 scripts/performance.py gate` 在真实用户配置的 GUI 服务器中运行声明 `:gate` 的场景（Ebox 与 ETAF 的 `benchmarks/performance-scenarios.el`），按 30/400/10k 行规模分别计时操作、强制重绘和操作分配；类别、预算与孪生对照见[工作区工具手册](manual.md#gate-a-change-in-the-gui)，真实配置运行方式见同手册的隔离 GUI 验证一节 | 局部绘制与同宽文字 p50 ≤ 50 µs、p95 ≤ 200 µs、≤ 200 cons 且与规模无关；Flex 内变宽文字 p50 ≤ 200 µs；Data 增量追加 ≤ 300 µs，快照追加 10k 行 ≤ 2 ms；计数器 ≤ 30 µs；挂载 ≤ 40 µs/行；400 行窗口缩放 ≤ 16 ms；端到端不超过同等直接 buffer 编辑 + 0.2 ms |
| Gallery 输入路径筛查 | `make -C etaf-ui perf-check` 通过通用工作区工具测量注册的回调、原生键盘命令和完整鼠标按下/释放场景；默认三组、每组十次独立挂载，记录命令开始至完成条件和强制 redisplay 返回，保留前后台、窗口、GC 和正确性事实；`--diagnose` 分别采集提供方阶段、CPU 与分配热点 | 复选框目标 50 ms，浮层目标 100 ms，500 ms 单独作为所有交互的硬底线；任何超标、无效或缺失样本均不得宣称通过。此命令用于首次交互筛查，不替代上述稳态分布和完整应用验收 |

GUI 测量遵循 ETAF 手册的[已有 GUI 动作测量契约](https://etaf.top/zh-cn/performance-engineering/#性能场景与预算)。必须让计时覆盖该动作引起的同步工作及实际显示提交；如果更新被调度到回调返回之后，不能在回调返回处提前停止计时。打开原生编辑器测到编辑界面可用，输入确认另测其处理与发布。用户思考和输入的时间、异步外部 IO 等待时间分别记录，不计入 50 ms 本地处理预算；请求启动和结果到达后的处理/发布分别受门槛约束，不能扣除回调中同步执行的数据库或其他计算工作。首次挂载另行报告，不能混入已预热的交互分布。

使用相同机器、代码 revision、数据、字体、GC 策略和记录模式比较改动前后结果；宽、窄窗口沿用现有 GUI 适配器的 1300×750 与 700×500 像素 frame 请求，并记录窗口管理器实际允许的 frame 和文本 viewport 尺寸。环境不能容纳时记录可复现的替代尺寸，两版及两种写法保持一致。resize 本身另行计时和检查，前台测量中的几何变化不能当成固定窗口动作的有效样本。

GUI 保持实际运行时的 GC 策略与用户设置，测量工具不能额外关闭或延后 GC、关闭必要工作或替换更小的列表达标；运行时自身的 GC 调度和整段操作中的 GC 耗时如实记录。批处理与 GUI 的 GC、代码加载和显示环境分别记录，不能据此相互认证。前台状态、目标窗口、字体或几何失效的样本保留为无效记录，修复条件后补足正式样本；所有有效慢样本保留，不得删除离群值或只选最快一组。GUI 还需报告包括首次使用与预热在内的全部样本数量、最大值、失败和拒绝原因。

每个正式样本必须真正执行其声明的操作并检查结果；通过交替输入或在计时外复位数据避免反复点击已选中行、保存相同值等空操作。复位不能预先完成被测查询、布局或发布工作。

每份结果记录仓库及评估器版本、环境、数据规模、操作、原始样本、预热/正式分类与 p50/p95/max，并与该操作的正确性检查关联。截图检查布局和显示，真实键鼠验证输入路径；回调计时不包含硬件输入到回调之前的延迟，redisplay 返回也不能证明操作系统已呈现画面。当前工具中缺少的异步发布、对照或采样能力属于待实现的验收工作，不能将表中的要求视为现成命令已覆盖。

### 11.4 整体完成条件

只有第 10.1 节所有必需项、第 11.1–11.2 节公共及用户流程、第 11.3 节适用门槛均有通过证据，才能标为完整交付。原型项必须有验证结论和可用替代方案，未纳入的扩展范围保持明确。正确性检查通过、某个演示可运行或已有批处理成绩，都不能单独证明生态重构完成。

最终组合需要在干净的 Emacs 环境分别验证源码安装和包归档安装，只添加包根目录即可加载入口及其声明依赖；消费者不加载提供方私有模块。已替代实现、旧示例调用和失实文档必须同步清理，工作区记录实际验证过的各仓库 revision。机器生成的检查、GUI 与性能证据放在版本控制之外，交付说明引用其位置和结果，不再新增过程报告文档。

## 12. 持续约束与交付

跨包开发先确定能力的责任方，再协调提供方公共接口和消费者；在集成检查点记录经过验证的仓库 revision。

代码审查必须检查职责与依赖方向、公共接口边界、状态和算法的所有权、失败更新与卸载语义、Ebox 独立使用能力，以及验收证据与能力声明的一致性。结构检查负责目录、引用和工具一致性；架构语义由公共行为验收与代码审查共同验证。

窗口或桌面功能的审查顺序固定为：先确认 Ebox 只提供几何/图层增量发布和手势输入事实，再确认 ETAF 的 Behavior 只把事实转换为受控状态，随后确认 ETAF UI 只提供可复用面板外壳，最后确认 `etaf-desktop` 才拥有窗口集合、工作区、层级及最大化/最小化策略。Playground 只能调用这些入口进行展示和验收，不得成为任何一层的隐式提供方。

本文维护已接受的目标契约。职责归属或公共语义发生变化时，说明设计依据并更新本文与相关包契约。各包文档保持与实现一致，本文持续更新尚未完成的开发要求。

## 13. 安装与分发契约

本节记录已接受的安装与分发目标契约。改动安装入口、归档内容、依赖处理或发布流程前先读本节；可执行命令见[工具手册](manual.md)。

### 13.1 单一入口

用户只面对一个入口：`M-x etaf-install`。`package.el` 是本项目的机制，不是并列推荐路径；文档只在一次性引导里出现 `package-install 'etaf-install`，因为安装器无法自举自己。菜单按框架、应用、游戏三段组织，候选文字以包名开头，便于按名字补全，末尾用括号标注分组；每个条目显示当前前提状态。目标的 `<包>-doctor` 返回与 `etaf-install-doctor` 相同的 `:required`/`:optional` 形状，由安装器合并展示；没有额外前提的目标可以不实现它。

### 13.2 依赖分为三类，各有归属

| 类别 | 例子 | 归属与机制 |
| --- | --- | --- |
| Emacs 包（自有或公共） | `etaf-db`、`telega` | 在 `Package-Requires` 声明；`etaf-install` 注册所需归档（`etaf`、`gnu`、`nongnu`、`melpa`），由 `package.el` 自动解析安装；不关闭签名校验、不改用户其它源。应用条目在 `workspace.json` 的 `applications` 段记录提交，框架提供方仍在 `repositories` 段 |
| 自有组件（CLI、Node 后端、可编译模块） | `weread` 后端、`ebook-parse`、EKP C 模块 | 源码放在**应用仓内**，随包同一 tar 发布并计入 sha256；安装到 `package-user-dir/etaf/<包>/<版本>/`；需要 `npm ci` 或 `make` 时在该目录执行，输出进日志、失败可重试；启动时握手校验组件版本与包版本一致 |
| 系统程序与账号 | ffmpeg、mpv、node、TDLib、Godot、OpenSpiel、平台登录 | 只检测，给出按平台生成的一条可复制命令；不代跑 `sudo`/`brew`/`apt`，不下载第三方二进制 |

自有组件的源码必须跟随应用仓，不留在别的仓库或技能目录：一个版本一次提升，Lisp 与组件原子发布，避免跨仓版本对齐。

### 13.3 版本不可变与来源可复算

任何源码变化都要提升包头部的 `Version`；发布器拒绝同名版本的不同字节。归档清单记录根仓封口提交、各提供方提交与每包 sha256，任何人可从对应 GitHub 提交重建并比对。发布前必须通过全量安装门禁；CI 的六格矩阵（Linux、macOS、Windows × Emacs 29.1、30.2）是平台证据，Windows 格不可省略，因为路径风格与 `load-path` 差异只在那一格暴露。

### 13.4 本地开发与正式发布是两条道

- dev：`scripts/package_archive.py build` 直接打包工作区，用于即时验证安装效果，产物不可发布。
- release：封口提交 → 提升版本 → `make release-build` → `make release-check` → `make release-publish`。

门禁拒绝未封口的工作区、缺失资源、过旧的依赖闭包、同名不同字节的证据；任何一环缺失就停在本地，不产生“看起来通过”的检查点。

### 13.5 缺依赖时怎么说

菜单条目直接显示状态；缺自有组件给一键安装，缺系统程序给一条命令并提示“装完回来按 `r` 重新检测”，缺账号交给应用内的一次性配置。阻塞与降级分开：缺 ffmpeg 只影响视频，允许打开并提示受限；缺 `telega-server` 或游戏引擎就明确拒绝启动。错误必须是一句人话加可复制命令，不输出 Lisp 堆栈。

### 13.6 明确不做

不代跑系统包管理器或 `sudo`，不静默改写用户配置（归档注册除外，且只增不减、不禁用签名），不关闭 TLS 或签名校验，不替换同名版本，不发布未封口代码，不把第三方二进制塞进归档。

### 13.6.1 发布清单的三层含义

`release-dependencies.json` 里 `packages` 是归档包含的全部包（含 `ebox`、`ecss` 这类依赖），`targets` 是用户真正安装的条目，只有它们需要安装证据；包所需的归档外依赖（例如 `telega` 来自 MELPA）必须在 `external` 里显式列出，闭包检查仍会拒绝未声明的缺包。安装诊断只对本归档发布的包负责：第三方依赖在安装时产生的过时宏警告不得阻塞发布，而我们自己的警告仍然失败。已安装包的入口在**编译期与加载期**都要能解析自己的 `lisp/`：编译期优先用 `byte-compile-current-file`，再回退 `load-file-name` 与 `buffer-file-name`（安装脚本本身可能仍在加载，`load-file-name` 会指向脚本而不是入口），否则 `package.el` 安装时会报 `Cannot open load file`。

### 13.7 当前差距

- 归档的安装目标覆盖框架、应用与游戏三段：框架 7 个包（`etaf-install`、`etaf-ui`、`etaf`、`ebox`、`ecss`、`ekp`、`etaf-db`），应用 7 个（`etaf-manual`、`etaf-md-preview`、`etaf-video-player`、`etaf-desktop`、`etaf-telega`、`etaf-weread`、`etaf-ncm`），游戏 2 个（`etaf-xiangqi`、`etaf-tanks`）。`etaf-gamekit` 随归档发布并由两个游戏声明为依赖，但不是独立安装目标。
- `etaf-telega` 通过声明 `telega` 与注册 MELPA 自动装齐依赖；`telega-server` 与账号仍未纳入（只检测）。
- `etaf-weread` 与 `etaf-ncm` 的后端已随应用仓发布，提示、数据目录与检测都指向包内后端；系统侧只检测 Node.js、mpv 等程序。
- `etaf-salvage` 与 `etaf-solitaire` 尚未纳入检查点，也没有引擎检测；`etaf-gamekit` 的引擎仍由用户在源码侧 `make` 构建。
- 组件的托管目录安装（`npm ci`/`make` 到 `package-user-dir/etaf/<包>/<版本>/`）与版本握手仍未实现。当前归档内的后端都是纯源码（Node、Python、Shell），随 tar 解包即可运行，所以这两个应用的“装完即用”不依赖它；需要托管安装的是将来带构建步骤的组件。

### 13.8 新增应用上架

固定步骤见[工具手册的安装分发流程](manual.md)：纳入检查点、声明依赖、放好资源、提升版本、跑安装门禁、发布、更新站点与检查点；不要临时发明第二条发布路径。

## 14. 应用与游戏集合

### 14.1 唯一工作区与检出位置

根仓库是唯一的集成根：框架包、应用与游戏都是本目录下的同级检出，逐个登记在
`workspace.json` 的 `repositories` 表里，`role` 取 `framework`、`application` 或
`game`。根 `make check` 按注册表顺序逐仓运行各自的 `check`，因此这张表同时是
检出清单、检查顺序和集成检查点。

不建立第二层工作区。嵌套的 `workspace.json` 会让注册表、共享检查工具和集成检查点
各长一份，结构检查会直接拒绝这样的目录；需要隔离副本的流程（发布、基准、验收）
创建一次性工作区并在结束后删除。提供者一律按同级解析（`../etaf`、`../etaf-ui`、
`../ebox`、`../ecss`），应用与游戏的 Makefile 保留 `../..` 回退只为兼容独立克隆。

### 14.2 职责与依赖方向

| 层级 | 仓库 | 职责 |
| --- | --- | --- |
| 应用 | `etaf-ncm`、`etaf-weread` 及各应用 | 具体产品的界面、交互与业务模型 |
| 游戏 | `etaf-tanks`、`etaf-xiangqi`、`etaf-solitaire`、`etaf-salvage`、`etaf-mario` | 游戏身份、玩法配置、内容资源、界面、局部交互状态与启动命令 |
| 游戏框架 | `etaf-gamekit` | 游戏定义、独立运行实例、通用后端适配、动作与观察结果、生命周期 |
| 组件 | `etaf-ui` | 可复用界面组件与主题 token |
| 运行时 | `etaf` | 组件、状态与挂载运行环境 |
| 布局与渲染 | `ebox` | 盒模型布局、绘制与增量发布 |
| 选择器语义 | `ecss` | 选择器与层叠语义 |

依赖方向只允许自上而下：应用与游戏依赖 ETAF UI、ETAF、Ebox 与 ECSS，游戏还依赖
GameKit；框架侧不得反向依赖任何应用或游戏，也不得因某个应用的需要改变框架的公共
接口。应用只通过提供者根入口声明的公共接口使用它们，未在 Commentary 中列出的符号
一律视为内部实现。添加应用通常只增加应用代码：只有实际用例证明缺少通用能力时，才
先在所属提供者补能力，再由应用使用；不得把应用或游戏的名称、规则、资源或专用开关
混进框架。

### 14.3 应用契约

每个应用以本目录下的同名目录独立检出，并满足：

- 根入口 `<名称>.el` 是唯一的包入口，实现放在 `lisp/`；入口 Commentary 是该应用公共
  API 的唯一清单，在同一处声明 `Function`、`Macro`、`Variable`、`Hook`、`Error`、
  `Component` 记录与 autoload 声明。
- `Makefile` 提供 `compile`、`test`、`check`、`clean`、`structure-check`、`setup-hooks`
  与 `api-check`；`check` 包含结构检查、字节编译、公共 API 边界检查和验收场景。
- 正确性场景集中在 `tests/` 与 `tests/acceptance.json`，只通过公共接口观察行为；数据
  样本放 `tests/fixtures/`，示例与非交互用法放 `examples/`。
- 与外部服务的交互由应用自己的服务层负责，界面与模型只依赖该层的公共接口，因此模型
  可以在无网络、无外部进程的条件下用注入的假实现驱动。
- 应用通过 `etaf-app-open` 打开：画布颜色、光标、mode line、随窗口稳定后的适配、关闭时的
  一次性释放与根 `:keys` 都由它承担；应用不再自带 major mode、face remap、display table、
  尺寸 hook 或 `kill-buffer-hook`，按键也不经 `emulation-mode-map-alists` 覆盖渲染器的映射。
- 应用自有、会增长的持久数据默认经 `etaf-db` 存取：元数据与正文分表，批量写入用
  `etaf-data-mutate-many` 只对账一次；后端权威数据只落本地派生值，远程列表用
  `etaf-list-cache`。存储访问留在应用自己的存储层，界面与模型只依赖其公共接口。

### 14.4 游戏契约

- 每款游戏提供完整的可玩回路：进入、操作、反馈、结束、重开和退出。规则使用成熟内核
  时，前端不再实现第二份合法性、碰撞、计分或胜负判定；界面只展示后端允许的操作。
  不用虚假的按钮、不可触发的控件或静态截图代替功能。
- 每款游戏同时支持浅色和深色主题，使用同一套语义 token 和组件结构；切换只更新呈现，
  保留实例、局面、选择、焦点、草稿和随机状态，不重启后端，也不修改用户的全局主题。
- 游戏世界与周边界面分开适配：牌、格子、棋子和精灵的固有尺寸在不同窗口中保持一致，
  宽度变化调整侧栏与信息密度，高度变化优先去掉次要说明，不挤压游戏元素。每款游戏
  声明最小可用窗口，低于它可以按结构裁切或滚动。
- 游戏经 `etaf-gamekit` 的单一挂载点成为同一应用运行时上的应用，因此不需要各自实现挂载与
  生命周期；保留 mode line 等既有呈现时，由 kit 在打开时显式声明，避免画布行数随之一并变化。
- 键盘和鼠标沿 ETAF 的公共输入路径工作，一个按键或一次激活只执行一次动作；高频状态
  更新只影响相关组件或保留节点；每个实例独立拥有进程、计时器和请求，关闭或杀死
  buffer 时释放资源，不影响其他实例。

### 14.5 验收与检查点

- 每个应用与游戏的 `make check` 通过，`make api-check` 能在批处理 Emacs 中加载公共
  入口并验证绑定与签名。
- 应用与游戏在真实图形 Emacs 中走通主要工作流，由人确认渲染与交互；批处理通过不代替
  GUI 外观，后台计时不代替前台输入延迟。游戏还需验证双主题、布局矩阵与独立实例。
- 服务层在外部服务或进程不可用时给出可读失败，而不是无声失败或破坏界面状态。
- `workspace.json` 记录地址、分支与已验证修订；应用与游戏的提交先在其仓库内完成检查
  并发布，再刷新检查点。本地未发布的仓库不是可复现的远端检查点。
